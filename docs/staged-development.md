# 段階的な開発の手順書（サブエージェント）

メインセッションのClaudeが、1つのissueを **計画 → 評価基準 → 実装 → 評価** の段階に分け、専用のサブエージェント（`.claude/agents/`）に任せて進めるときの手順。issue #25（2026-10）の試験運用の振り返り（`docs/issues/closed/25-groove-tracking/retrospective.md`）をもとに作った。

ルールは `docs/rules/`、受け渡しフォルダの運用は [`issues/README.md`](issues/README.md)、gitの操作は [`git-rules.md`](git-rules.md) に従う。この手順書は、それらを段階の流れに沿って並べ、メインがすることを書いたもの。

## 1. 使う場面

- **使う**：複数のファイルにまたがる機能の追加や、アルゴリズムの選択・実データでの評価が要る作業（`feature` のissueなど）。
- **使わない**：1回のセッションで終わる小さな変更、ドキュメントだけの変更、命名の整理（`refactor` は `matlab-refactor` エージェントか、メインが直接行う）。

## 2. 登場するもの

| 担当 | 定義 | 段階 | 書くもの（受け渡しフォルダ `docs/issues/<番号>-<slug>/`） | ほかに書くもの |
|---|---|---|---|---|
| main（メインセッション） | — | すべて | `README.md`（作業履歴、ファイル一覧）、`retrospective.md`、`follow-ups.md` | コミット、push、PR、issueへのコメント |
| planner | `.claude/agents/planner.md` | 計画 | `plan.md` | なし |
| evaluator（モードA） | `.claude/agents/evaluator.md` | 評価基準 | `criteria.md` | `test/unit/*AcceptanceTest.m`、`scripts/evaluation/<テーマ>/` |
| implementer | `.claude/agents/implementer.md` | 実装 | `impl-report-<n>.md` | `src/`、`scripts/`、`test/unit/*Test.m`、README |
| evaluator（モードB） | `.claude/agents/evaluator.md` | 評価 | `eval-report-<n>.md` | `experiments/`（指示されたデータ）、`results/<日付>/`、`temp/` |
| summarizer | `.claude/agents/summarizer.md` | 仕上げ | `README.md` の「解決のまとめ」の節 | なし |

サブエージェントはコミット・push・ブランチの切り替えをしない。ユーザーに直接質問もできない（未決事項として報告し、メインがユーザーに尋ねる）。

## 3. 全体の流れ

```
0. 準備：issue → 作業ブランチ → 受け渡しフォルダ
1. 計画（planner） ─────────────→ [ユーザーが承認] → コミット
2. 評価基準（evaluator A） ─────→ [ユーザーが承認] → コミット
3. 実装（implementer） ─────────→ [ユーザーが報告を確認] → コミット
3a.（必要なときだけ）ユーザーがデータを作る ─→ [メインが記録を確認] → コミット
4. 評価（evaluator B） ─────────→ [ユーザーが目視・試聴] → コミット
      └ 不合格なら 3 に戻る（最大3回。超えたらユーザーに相談）
5. 仕上げ：振り返り → 続きのissue → 解決のまとめ（summarizer） → closed/ へ移動 → PR → [ユーザーがマージ]
```

### ユーザーの確認を挟む場所

| 区分 | 場所 |
|---|---|
| **必ず挟む** | issueの未決事項、計画の承認、評価基準の承認、ユーザーがデータを作る前の日付と手順の確認（5.5）、ユーザーが判断する項目（図・スペクトログラム・試聴など）、issueに書かれていないデータの作成・削除・上書き、push、PRの作成（マージはユーザーが行う） |
| **ユーザーが省いてよいと言えば省ける** | エージェントを呼ぶ前の確認、依頼文の事前の提示、段階ごとのコミットの確認 |

省いてよい範囲は、issueごとにユーザーに確かめ、受け渡しフォルダの `README.md` の作業履歴の「準備・全体」に **決定** として書いておく。書かれていなければ、すべて確認する。

## 4. 準備（段階0）

1. **issueを立てる**（必須。受け渡しフォルダの置き場所がissue番号で決まるため）。ひな型は `.github/ISSUE_TEMPLATE/`。未決事項があれば、ユーザーに確かめる。
2. **作業ブランチを作る**：masterから `claude/<slug>`。worktreeは使わない（MATLABを1つ共有しているので、エージェントは順に動かす）。
3. **受け渡しフォルダを作る**：`docs/issues/<番号>-<slug>/README.md` を、[`issues/README.md`](issues/README.md) の「README.md の書き方」のひな型で作る（解決のまとめ、作業履歴、ファイル一覧）。コミットする。

## 5. 各段階でメインがすること

### 5.1 共通

**呼ぶ前**
- masterにルールやエージェント定義の変更が入っていれば、作業ブランチに `git merge master` で取り込む（エージェントは、チェックアウト中のブランチのファイルを読む。進捗ログのコミットだけなら、取り込まなくてよい）。
- 新しく作ったエージェント定義は、セッションを開き直すまで呼べないことがある。呼べなければ、セッションを開き直す。
- `git status --porcelain` が空であることを確かめる（特に評価の前）。
- その段階の成果物（`plan.md`・`criteria.md` など）が、受け渡しフォルダにすでに無いかを確かめる。会話を巻き戻したときや別のセッションでの実行で、作業履歴に無い成果物が残っていることがある（#30）。あれば呼ばずに止め、ユーザーに確かめる。
- 依頼文を作る（6章の型）。

**呼んだ後**
- 最後の報告が返ってこなければ、報告を返すよう依頼する（`SendMessage`）。同じセッションでなければ再開できないので、そのときは受け渡しファイルを読んで代わりにまとめる。
- `git status`・`git diff` で、書いてよい範囲の外のファイルが変わっていないかを確かめる。
- 報告と受け渡しファイルの「結論」を読み、ユーザーに要点・未決事項・確認してほしいファイルを伝える。
- ユーザーの決定を受け渡しファイルに反映する（状態を「承認済み」にする、決定事項を書く）。受け渡しフォルダの `README.md` の作業履歴に、エージェントの作業とユーザーの決定（**決定**）の項目を足し、見出しの状態を更新する。新しいファイルができたら、ファイル一覧にも足す。
- コミットする。末尾に、関わったエージェントを `Agent: <名前>` で書く（`git-rules.md` のルール6）。pushはユーザーに確かめてから。

**修正を頼むとき**
- 同じセッションなら `SendMessage` で続きを頼める。セッションが変わっていたら、新しく呼び、修正の内容をすべて依頼文に書く（前の会話を前提にしない）。

### 5.2 計画（planner）

- 依頼文には、issue作成後にユーザーと決めたことをすべて書く（issue本文より優先することを明記する）。
- `plan.md` の未決事項をユーザーに尋ね、決まったら8章を「決定事項」に、状態を「承認済み」にする。
- 正式なデータ（`experiments/` に残すもの）の作成が、評価の段階に割り当てられていることを確かめる（`docs/rules/data.md` の「実データの記録と作業ツリー」）。
- ユーザーが作るデータ（保存した選択では再現できない `ginput` が要るもの）があれば、使うスクリプト、クリックの回数、作る時期（通常は実装のコミットの後、評価の前）が `plan.md` に書かれていることを確かめる（5.5）。

### 5.3 評価基準（evaluator モードA）

- `criteria.md` のしきい値が、「計画どおりかの確認」と「品質の基準」に分けて書かれているかを確かめる。
- 承認されたら、`criteria.md`・受け入れテスト・評価スクリプトをコミットする。そのあと、`criteria.md` の `<受け入れテストを追加したコミット>` を、そのコミットのハッシュに書き換えてコミットする。
- このコミットの後、作業ブランチの `runAllTests` は、実装が終わるまで受け入れテストの分だけ失敗する（正常）。

### 5.4 実装（implementer）

- 実装担当は `experiments/` に保存しない。実データでの動作確認は、`temp/` のコピーで保存の行を外して行う。
- 報告を確かめたら、実装をコミットする（`Agent: implementer`）。評価はこのコミットの後に行う。

### 5.5 ユーザーがデータを作る（必要なときだけ）

- **必要になる場合**：評価に使うデータ（正解データなど）を作るのに、保存した選択（cycleResult の `grooveSelection`）では再現できない `ginput` が要るとき。`ginput` が要るスクリプトはエージェントもメインも実行しない（`docs/rules/data.md`）ので、ユーザーが実行する。例：#30 の正解データ（2〜N本目の溝を写真ごとにクリック、計40回）。保存した選択で再現できるデータは、評価担当が作る（5.6）。
- **時期**：計画で決める（5.2）。使うスクリプトを実装で作るときは、実装のコミットの後、評価の前。
- **事前に、メインがユーザーに伝えること**
  - 実行するスクリプトと、`temp/` のコピーで変える行（日付、ガイドに使う結果のパスなど）
  - 使う日付（MMDD）。`experiments/<日付>/`・`results/<日付>/` に同じ名前のファイルが無いことを、メインが先に確かめる
  - 作業ツリーがきれいなこと（`git status --porcelain` が空。MATLABのエディタに未保存の変更が無い）
  - 実行した後にユーザーが見る図と観点（溝の飛び移りが無いか など）
- **事後に、メインが確かめて作業履歴に書くこと**
  - `meta.gitCommit` が実装のコミットの後で、そこから `src/`・`scripts/`・`test/` に差分が無いこと
  - `meta.gitDirty = false`
  - `_2` 付きのファイル（同じ名前を避けて別名で保存されたもの）が無いこと
  - ユーザーが図を確かめた結果（評価の前提になるので **決定** として書く）
- 問題があれば、評価担当を呼ぶ前に、作り直すかをユーザーに相談する。

### 5.6 評価（evaluator モードB）

- **日付**：評価を実行する日（MMDD）を使う。`experiments/<日付>/`・`results/<日付>/` に同じ名前のファイルが無いことを確かめる。ぶつかる場合は、別の日に評価する。
- **作業ツリー**：きれいな状態で始め、データを作り終えるまでは追跡される場所にファイルを作らないよう、依頼文に順番を書く。日付などを書き換えたスクリプトのコピーは `temp/` に置く。
- 判定が「ユーザー確認待ち」なら、ユーザーに見てほしいファイルと観点を伝える。ユーザーの確認の結果は、メインが `eval-report-<n>.md` の先頭に追記する（評価担当の本文は変えない）。
- 不合格なら、`eval-report-<n>.md` を入力に implementer を `<n+1>` 回目として呼ぶ。

## 6. 依頼文の型

どの段階も、次の共通部分から始める。依頼文は、それだけで意味が通るように書く。

```
<モード／段階> で、issue #<番号> をお願いします（<n>回目）。

- issue番号: <番号>（`gh issue view <番号> --comments`）
- 受け渡しフォルダ: `docs/issues/<番号>-<slug>/`（読むべきファイル、特に README.md の作業履歴の **決定**）
- 現在のブランチ: `claude/<slug>`（切り替えない。コミット・pushもしない）

## issue作成後にユーザーと決めたこと（issue本文より優先）
- ...

## 手順・補足
- （段階ごとの指示。順番に意味があるときは番号を振り、理由も書く）
- MATLAB は今あなただけが使ってよい。`Research.prj` が開いていなければ `openProject` で開いてよい。
- 作業の最後に、必ず最後の報告を返すこと。
```

段階ごとに足すもの：
- **計画**：参考にするブランチやコード、比べてほしい観点、実データで試してよい範囲。
- **評価基準**：作るもの（`criteria.md`、受け入れテストの対象、評価スクリプトのテーマ名）、正解データ、ユーザーが判断する項目の候補。
- **実装**：`plan.md` のどの手順まで行うか、実データでの動作確認の範囲（`experiments/` に保存しないこと）。
- **評価**：日付、作るデータのファイル名と作り方、作業ツリーをきれいに保つ順番、`temp/` の使い方。
- **解決のまとめ**：差分の範囲（既定 `master...HEAD`）、PR番号（あれば）、書き込み先（既定は README の節）、作業履歴に書かれていない会話の決定（できれば、呼ぶ前に作業履歴へ書いておく）。MATLABの行は要らない（summarizer は MATLAB を使わない）。

## 7. 仕上げ（段階5）

1. **振り返り**：`retrospective.md` に、経過（所要時間・トークン）、うまくいったこと、問題と学び、ルール・定義の改善案を書く。改善案はユーザーが決め、採用したものはmasterで反映して作業ブランチに取り込む。小さなissueでは簡単でよい。
2. **続きのissue**：作業中に出た案を `follow-ups.md` などにメモし、作るタイミングとあわせてユーザーに確かめる。
3. **解決のまとめ（summarizer）**：`closed/` の README だけを読めばissueをどう解決したかが分かるように、README の「解決のまとめ」の節を書いてもらう。書き方は [`issues/README.md`](issues/README.md) の「README.md の書き方」。
   - 呼ぶ前：`retrospective.md`・`follow-ups.md`・作業履歴が最新であることを確かめる。会話で決めて作業履歴に書いていないことがあれば、先に書く（summarizer は会話を知らず、記録だけから書くため）。`git status --porcelain` が空であることを確かめる。
   - 呼んだ後：`git diff` で、README の「解決のまとめ」の節の外が変わっていないことを確かめる。報告の「記録の抜け・食い違い」をユーザーに確かめ、作業履歴かまとめに書き足す。まとめをユーザーに見せる。コミットする（`#<番号> の解決のまとめを README に書く`、`Agent: summarizer`・`Agent: main`）。
   - この後にコードが変わったら（Auto-fix など）、メインがまとめの「5. 計画から変わったこと」に1行足し、対象のコードの SHA を書き換える。
4. **closed/ へ移す**：PRの最後のコミットで `git mv docs/issues/<番号>-<slug> docs/issues/closed/<番号>-<slug>`。フォルダの外からのリンクがあれば、同じコミットで書き換える。
5. **PRを作る**：本文に目的・背景と `Closes #<番号>` を書く（解決のまとめの1・2節を元にしてよい）。作成はユーザーに確かめてから。マージはユーザーが行う。

## 8. 注意点

- **進捗ログの自動コミット**：スケジュールタスク `progress-report-daily` は、常にmasterにコミットする（issue #27）。作業ブランチをチェックアウトしていると、書き込みが要る日だけ一時的にmasterへ切り替えて、元のブランチに戻す。作業ブランチに進捗ログのコミットは入らない。作業ブランチのコミットは、mergeを待たずに、そのコミットの日付で `[ブランチ名]` を付けて進捗ログに載る（GitHubだけにあるブランチも含む）。追跡されているファイルに未コミットの変更を残したまま夜を越すと、その日は見送りになり、通知が来る。切り替えの間はファイルが一時的に変わるので、MATLABのエディタに未保存の変更を残さない。
- **MATLABは1つ**：エージェントを並列に動かさない。メインも、エージェントが動いている間はMATLABを使わない。
- **セッションをまたぐ**：前のセッションのエージェントは再開できない。経過は受け渡しフォルダの `README.md` の作業履歴に残し、次のセッションはそこから読む。
- **ルールの置き場所**：エージェントに守らせたいことは、メインの個人メモリではなく `docs/rules/` かエージェント定義に書く（エージェントはメモリを読めない）。

## 9. 検討中のこと

- **コードレビューの段階**：評価担当は動作と数値を確かめるが、コードの読みやすさや `docs/rules/coding.md` を守っているかは見ていない。実装の後に `/code-review` などで差分をレビューする段階を足すかを検討する。

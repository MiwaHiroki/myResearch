# docs/issues/ — issueごとの作業フォルダ

## 目的

1つのissueを複数の段階（計画、評価基準の作成、実装、評価 など）に分けて進めるときに、段階のあいだで受け渡すファイルを置く場所。サブエージェントは毎回会話の記憶なしで始まるので、ここに置いたファイルが段階をまたぐ唯一の引き継ぎ手段になる。作業が終わった後は、そのissueで何を検討し、どう判断したかの記録として残す。

小さなissue（1回のセッションで終わるもの）では作らなくてよい。

## 構成

```
docs/issues/
├── README.md                 このファイル
├── <番号>-<slug>/            作業中のissue
│   ├── README.md             issueへのリンク、ブランチ名、各ファイルの一覧と状態
│   └── ...                   各段階の成果物
└── closed/
    └── <番号>-<slug>/        closeしたissue（中身はそのまま）
```

- フォルダ名は `<issue番号>-<内容を表す短い英語スラッグ>`（例: `42-groove-tracking`）。スラッグは作業ブランチ `claude/<slug>` と揃える。
- `docs/issues/` の直下にあるフォルダ（`closed/` を除く）が、作業中のissue。
- 各段階の成果物のファイル名（計画、評価基準、評価レポート など）は、その段階を担当するエージェントの定義（`.claude/agents/`）で決める。

## 運用の流れ

1. **作る**: issueに着手するとき、作業ブランチ上で `docs/issues/<番号>-<slug>/README.md` を作る。
2. **使う**: 各段階の成果物をこのフォルダに書き、作業ブランチにコミットする。コミットのルールは [`../git-rules.md`](../git-rules.md) に従う。
3. **閉じる**: PRの最後のコミットで、フォルダを `closed/` に移す。
   ```bash
   git mv docs/issues/<番号>-<slug> docs/issues/closed/<番号>-<slug>
   ```
   PR本文に `Closes #<番号>` を書いておくと、PRのマージと同時にissueもcloseされる。フォルダはPRと一緒にmasterへマージする。

## リンクの書き方（移動でリンクが切れないようにする）

`closed/` への移動でパスが変わるため、リンクは次のように書く。

| リンクを書く場所 | 書き方 |
|---|---|
| フォルダ内のファイル同士 | 相対パス（`./plan.md` など）。フォルダごと移動するので切れない |
| issueのコメント・PR本文 | コミットSHA付きのパーマリンク（`https://github.com/MiwaHiroki/myResearch/blob/<SHA>/docs/issues/...`）。ブランチ名入りのURLは使わない |
| フォルダの外（README、他のdocs など） | なるべく書かない。書く場合は、移動するコミットで書き換える |

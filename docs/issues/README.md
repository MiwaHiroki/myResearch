# docs/issues/ — issueごとの作業フォルダ

## 目的

1つのissueを複数の段階（計画、評価基準の作成、実装、評価 など）に分けて進めるときに、段階のあいだで受け渡すファイルを置く場所。サブエージェントは毎回会話の記憶なしで始まるので、ここに置いたファイルが段階をまたぐ唯一の引き継ぎ手段になる。作業が終わった後は、そのissueで何を検討し、どう判断し、どう解決したかの記録として残す。**`closed/<番号>-<slug>/README.md` だけを読めば、そのissueをどう解決したか、どの文書を誰がいつ書いたかが分かる**ようにする。

小さなissue（1回のセッションで終わるもの）では作らなくてよい。

サブエージェントで段階的に進めるときの全体の手順は [`../staged-development.md`](../staged-development.md) を参照。

## 構成

```
docs/issues/
├── README.md                 このファイル
├── <番号>-<slug>/            作業中のissue
│   ├── README.md             解決のまとめ、作業履歴、ファイル一覧（下の「README.md の書き方」）
│   ├── progress-material.md  進捗報告の素材（作るissueだけ。下の「progress-material.md の書き方」）
│   ├── follow-ups.md         続きのissueの案（仕上げで書く。下の「follow-ups.md の書き方」）
│   └── ...                   各段階の成果物
└── closed/
    └── <番号>-<slug>/        closeしたissue（中身はそのまま。follow-ups.md の案の状態だけは更新する）
```

- フォルダ名は `<issue番号>-<内容を表す短い英語スラッグ>`（例: `42-groove-tracking`）。スラッグは作業ブランチ `claude/<slug>` と揃える。
- `docs/issues/` の直下にあるフォルダ（`closed/` を除く）が、作業中のissue。
- 各段階の成果物のファイル名（計画、評価基準、評価レポート など）は、その段階を担当するエージェントの定義（`.claude/agents/`）で決める。ただし、main と illustrator が書く進捗報告の素材 `progress-material.md` と、main が書く続きのissueの案 `follow-ups.md` は、このファイルの「progress-material.md の書き方」「follow-ups.md の書き方」で決める。

## 運用の流れ

1. **作る**: issueに着手するとき、作業ブランチ上で `docs/issues/<番号>-<slug>/README.md` を、下の「README.md の書き方」のひな型で作る。「解決のまとめ」は見出しと1行だけにしておく。
2. **使う**: 各段階の成果物をこのフォルダに書き、作業ブランチにコミットする。エージェントの作業やユーザーの決定のたびに、README の作業履歴に項目を足し、見出しの状態を更新する。コミットのルールは [`../git-rules.md`](../git-rules.md) に従う。
3. **閉じる**: その前に「解決のまとめ」を書く（`summarizer` エージェント。[`../staged-development.md`](../staged-development.md) 7章）。PRの最後のコミットで、フォルダを `closed/` に移す。
   ```bash
   git mv docs/issues/<番号>-<slug> docs/issues/closed/<番号>-<slug>
   ```
   PR本文に `Closes #<番号>` を書いておくと、PRのマージと同時にissueもcloseされる。フォルダはPRと一緒にmasterへマージする。
4. **閉じた後**: `closed/` の中身は変えない。ただし、`follow-ups.md` の案からissueを作ったときと、案を見送ると決めたときは、その案の状態を更新する（下の「follow-ups.md の書き方」）。

## リンクの書き方（移動でリンクが切れないようにする）

`closed/` への移動でパスが変わる（階層が1つ深くなる）ため、リンクは次のように書く。

| リンクを書く場所 | 書き方 |
|---|---|
| フォルダ内のファイル同士 | 相対パス（`./plan.md` など）。フォルダごと移動するので切れない |
| issueのコメント・PR本文 | コミットSHA付きのパーマリンク（`https://github.com/MiwaHiroki/myResearch/blob/<SHA>/docs/issues/...`）。ブランチ名入りのURLは使わない |
| フォルダの中からフォルダの外（`src/`、他のdocs など） | 相対リンクにしない（`../../staged-development.md` は `closed/` へ移すと切れる）。リポジトリのルートからのパスをバッククォートで書く（`docs/staged-development.md`、`src/extractMultiGroove.m`） |
| フォルダの外からフォルダの中 | なるべく書かない。書く場合は、移動するコミットで書き換える |

## README.md の書き方

### 構成

上から次の順に書く。

| 節 | 書く人・時期 | 役割 |
|---|---|---|
| メタデータ | main、作るとき | `docs/rules/communication.md` の5項目（段階: 準備、作成者: main、作成日、入力: issue #<番号>、状態: 作業中／完了） |
| タイトルとリンク | main、作るとき | `# #<番号> <issueのタイトル>`、issue・ブランチ・PR・手順書へのリンク |
| 解決のまとめ | summarizer が下書きし、main が確かめる。仕上げで | どう解決したか |
| 作業履歴 | main、作業のたび | 文書・作業ごとの、いつ・誰が・何をしたか／何を決めたか（表）。段階の状態もここに書く |
| ファイル一覧 | main、ファイルができたとき | フォルダの中のファイルの索引 |

一般的な進め方は `docs/staged-development.md` へのリンクだけにし、README には書き写さない。issue固有の進め方（例：正解データはユーザーが `ginput` で作る）は、作業履歴の「準備・全体」に書く。

### ひな型

````markdown
- 段階: 準備
- 作成者: main
- 作成日: YYYY-MM-DD
- 入力: issue #<番号>
- 状態: 作業中

# #<番号> <issueのタイトル>

- issue: [#<番号> <issueのタイトル>](https://github.com/MiwaHiroki/myResearch/issues/<番号>)
- ブランチ: `claude/<slug>`
- PR: （作ったら書く）
- 進め方: `docs/staged-development.md`、受け渡しフォルダの運用: `docs/issues/README.md`

## 解決のまとめ

仕上げで書く（summarizer）。

## 作業履歴

### 準備・全体 — 完了

| 日付 | 担当 | 内容 | 成果物 |
|---|---|---|---|
| YYYY-MM-DD | main | issue #<番号> を受け、ブランチ `claude/<slug>` と受け渡しフォルダを作る | `README.md`、`<SHA>` |
| YYYY-MM-DD | ユーザー | **決定** 確認を省く範囲：… | — |

### 計画 — 未着手
### 評価基準 — 未着手
### 実装 — 未着手
### 評価 — 未着手
### 振り返り — 未着手
### 続きのissue — 未着手
### 解決のまとめ — 未着手
### 仕上げ（closed/ へ移動・PR） — 未着手

## ファイル一覧

- `README.md`：このファイル
````

### 解決のまとめ

作業中は見出しと「仕上げで書く（summarizer）」の1行だけを置き、仕上げで summarizer がこの節を置き換える。メインが確かめ、記録の抜けを書き足す。詳細は書き写さず、受け渡しファイルの章を示して済ませる。

読み手は、実装をClaudeに任せた人や、このissueに関わっていない人。**どういう考えで、何をしているか**が分かることを一番にする。

分量の配分（全体の目安は 100〜180 行）：
- **3節「採った方法」を最も厚くする**（全体の4割以上）。
- 4節「変えたファイル」は短くする（表のほかは10行程度）。コード（関数の呼び出し方の例など）は書かない。テストやドキュメントの更新は1行にまとめる。
- ほかの節は要点だけにする。

```markdown
## 解決のまとめ

- 書いた日: YYYY-MM-DD（summarizer が下書き、main が確認）
- 対象のコード: `<SHA>`（この時点の `claude/<slug>` の先頭。PR #<番号>）

### 1. 結論
何ができるようになったか、どんな方法で実現したか、評価の結果（何回目で合格したか）を2〜4文で書く。

### 2. 問題とゴール
issue のゴールと背景を2〜3文で書く（issue を開かなくても分かるように）。

### 3. 採った方法

#### 考え方
何を手がかりにして、どう解いたのかを、変数名や式を使わずに数文で説明する。

#### 処理の流れ
入力から出力までを、番号付きの手順で書く。各手順は、どの関数・スクリプトが行うかを名前で示し、何をするのかと、なぜそうするのかを短く書く。
1つの手順の中の細かい順番は (1)(2)…、場合分けは (a)(b)… で書く（`docs/rules/writing.md` の「番号」）。関数が何を受け取り何を返すかも、ここで文章で書く。
判定の条件や数値は、その意味を言葉で説明し、パラメータの名前を添える。

#### 選んだ理由と、採らなかった案
案ごとに、どんな方法か、試した結果（数値）、採らなかった理由を書く（plan.md の案の比較から）。

#### 主なパラメータ
| 名前 | 値 | 意味 | 決めた根拠 |
|---|---|---|---|

### 4. 変えたファイル
| 区分 | パス | 役割 |
|---|---|---|
（主なコード、つまり `src/` の関数・クラスと `scripts/` のスクリプトだけを、1ファイル1行で書く。
リポジトリの外で変えたもの（例：タスクのプロンプト・許可設定）も入れる）

保存形式の変更と、今までのデータとの互換性を、分類ごとにまとめた箇条書きで、要点だけ書く。
コード（関数の呼び出し方の例など）は書かない。関数の使い方は3節の処理の流れで文章で書く。
テスト・ドキュメント（README、CLAUDE.md など）・受け渡しフォルダの更新は、表に入れず1行にまとめる。

### 5. 計画から変わったこと
実装・評価・仕上げの途中で plan.md から変えた点と、その理由を書く（差し戻しを含む）。
結果・使い方・保存形式に影響する違いを書き、影響しない細部（内部の変数名など）は書かない。無ければ「なし」と書く。

### 6. 評価の結果
合否、主な数値としきい値、ユーザーの確認（目視・試聴）の結果、評価に使ったデータの場所を書く。

### 7. 使い方
何をどう実行すればよいかを、番号付きの手順の文で書く（例：「MATLAB で `Research.prj` を開き、`scripts/xxx.m` の冒頭の `date` を実行日にして実行する。」）。
設定するパラメータ、出力の場所、ルートの README の節名も書く。コードでないissueは「動き方と確かめ方」にする。

### 8. 制約と残った課題
分かっている制約と、follow-ups.md の案を、1つずつ書く。

### 9. 詳しく読むには
読む目的（経過と振り返り、問題とゴール、方法・パラメータ、評価基準、実装、評価）ごとに、どのファイルのどの章を読めばよいかを1行ずつ書く。
最後に、主なコミットの SHA を1行で並べる。
各節はほぼ段階ごとの受け渡しファイルに対応しているので、節ごとの出典は書かない。所要時間やトークン数も書かない。
```

ルール：
- **自然で分かりやすい日本語で書く。** 受け渡しファイルの表現をそのまま写さず、このissueを知らない人が読んで意味が通る文に書き直す。書き方の詳細は `.claude/agents/summarizer.md` の「文章」に従う（メインが確かめるときも同じ）。
- **根拠のあることだけを書く。** 受け渡しファイル・issue・差分・コードのどれにも無いことは書かず、「記録なし」とする。計画とコードが食い違えばコードを正とし、5節に書く。
- 名前とパスは、対象のコードの SHA の時点のものを書く（後でリネームされても `git show <SHA>:<パス>` でたどれる）。数値は出典と同じ桁で写す。
- 新しく出てくる記号・変数は、初出で意味を書く。
- 当てはまらない節は、見出しを残して「該当なし」と書く。
- 仕上げの後でコードが変わったら（Auto-fix など）、メインが5節に1行足し、対象のコードの SHA を書き換える。

### 作業履歴

段階の状態と決定事項・申し送りを、**文書・作業ごとに**まとめる。見出しごとに、いつ・誰が・何をしたか／何を決めたか・何を書いたかを、日付順の**表**にする。見出しに今の状態を書くので、見出しを追えば段階の状態が分かる。

```markdown
## 作業履歴

### 計画 — 承認済み

| 日付 | 担当 | 内容 | 成果物 |
|---|---|---|---|
| 2026-10-26 | planner | `plan.md` を書く（1回目） | [`plan.md`](./plan.md) |
| 2026-10-27 | ユーザー | **決定** 承認。Q1〜Q4 はすべて推奨どおり（`BIN_WIDTH = 1`・`BAND_TOL = 3`）。<br>理由や細目は、このように同じセルの中で改行して続ける | — |
| 2026-10-27 | main | 決定を `plan.md` 8章に書き、状態を「承認済み」にしてコミットする | [`plan.md`](./plan.md)、`22aa553` |

### 実装 — 完了（1回目）

| 日付 | 担当 | 内容 | 成果物 |
|---|---|---|---|
| 2026-10-28 | implementer | 1回目。`runAllTests` 217件すべて通過 | [`impl-report-1.md`](./impl-report-1.md) |
| 2026-10-28 | main | 報告を確かめ、実装をコミットする | `560e085` |
```

ルール：
- **見出し**：`### <作業> — <状態>`。作業は次の順に並べる：準備・全体、計画、評価基準、実装、評価、進捗報告の素材（素材を作るissueだけ）、振り返り、続きのissue、解決のまとめ、仕上げ（closed/ へ移動・PR）。進捗報告の素材は、計画と評価の両方の区切りで作るので、その作業とユーザーの決定を1つの見出しにまとめる。issue固有の作業（例：ユーザーが行う正解データの作成、リポジトリの外への反映）は、行われる位置に足す。番号は振らない（足したときに振り直さなくてよいように）。
- **状態**：未着手／作業中／下書き／承認済み／完了／合格（n回目）／不合格（n回目）。
- **表**：列は「日付・担当・内容・成果物」の4つ。1つの作業・決定を1行にし、同じ見出しの中は日付順に並べる。まだ行の無い見出し（未着手のもの）は、見出しだけを置き、最初の行ができたときに表を作る。
  - **日付**：`YYYY-MM-DD`。
  - **担当**：エージェント名（evaluator は `evaluator（A）`・`evaluator（B）` とモードも）、`main`、`ユーザー`。
  - **内容**：何をしたか、何を決めたか。理由や細目は同じセルの中で `<br>` で改行して続ける。内容に `|` を書くときは `\|` にする（表の区切りと見なされるため）。
  - **成果物**：その行で書いた・変えたもの。フォルダの中は相対リンク、外はバッククォートのパス、コミットは SHA。無ければ `—`。
- **決定**：ユーザーやメインが決めたことは、内容の頭に **決定** を付ける（`決定` で検索すれば一覧できる）。決定は、それが**効く作業**の見出しの下に書く（例：実装の後に評価の日付を決めたら「評価」の下）。全体に効くもの（確認を省く範囲など）は「準備・全体」の下に書く。
- **差し戻し**：実装・評価の2回目以降は、同じ表に「（2回目）」の行として続ける。
- **長い記録**（調べたことのメモなど）は、フォルダの中の別のファイル（例：`notes.md`）に分け、その行の成果物の列からリンクする。

### ファイル一覧

フォルダの中のファイルを、相対リンクと内容の1行で並べる。作者・日付・状態は作業履歴に書くので、ここには書かない（二重に管理しないため）。フォルダの外のもの（受け入れテスト、評価スクリプト、コード）は、作業履歴の表の成果物の列に書く。

```markdown
## ファイル一覧

- `README.md`：このファイル
- [`plan.md`](./plan.md)：計画
- [`criteria.md`](./criteria.md)：評価基準
- [`impl-report-1.md`](./impl-report-1.md)：実装の報告（1回目）
- [`progress-material.md`](./progress-material.md)：進捗報告の素材
```

## progress-material.md の書き方

進捗報告の素材を、issue の作業の区切りでためていくファイル。**素材**は、指導教員への進捗報告で使う図か表の1つである。素材ファイルは、進捗報告のスライドの材料になり（skill `make-progress-slides`）、ユーザーが実装の中身を理解する助けにもなる。

- 置くのは、研究の内容に関わるissueのうち、準備の段階でユーザーが素材を作ると決めたものだけである（`docs/staged-development.md` 5.7）。
- main が素材の項目を作り、状態を管理する。MATLAB で作る図と、その説明は illustrator が書く。手順は skill `progress-material`（`.claude/skills/progress-material/SKILL.md`）にある。
- 素材についての作業とユーザーの決定は、`README.md` の作業履歴の「進捗報告の素材」の見出しに書く。素材ファイルには経過を書かない（二重に管理しないため）。

### 構成

上から次の順に書く。本文の節を `docs/rules/slides.md` の「説明の順」と同じにするのは、スライドを作るときに、この順に読めばよいようにするためである。

| 節 | 書くこと |
|---|---|
| メタデータ | `docs/rules/communication.md` の5項目（段階: 進捗報告の素材、作成者: main・illustrator、作成日、入力: issue #<番号> と元にした受け渡しファイル、状態: 作業中／完了） |
| タイトル | `# #<番号> <issueのタイトル> — 進捗報告の素材` |
| 言葉 | 素材の中で何度も使う言葉の定義（`docs/rules/writing.md`）。無ければ節ごと省く |
| 本文 | `## 1. 実装内容の説明`、`## 2. 結果`、`## 3. 結果の考察`、`## 4. 検討事項・今後の方針`、`## 5. 補足・参考事項` の5つの節。素材が無い節も、見出しを残す |

### 素材のひな型

各節の下に、1つの素材を1つの見出しにして並べる。

````markdown
### M<番号> <伝えること> — <状態>

<示すこと。この図・表から何が分かるかを、issue を知らない人に向けて1〜3文で書く>

| 図 | 作り方 |
|---|---|
| `results/figures/progress/<テーマ>/<名前>.png` | `scripts/progress/<名前>.m` を YYYY-MM-DD に実行した。読んだデータは `experiments/<MMDD>/<ファイル名>` |

- スライドでの使い方
  - 図の上の説明の案は「<説明>」である。
  - <強調したい所を、何が図のどのあたりにあるかとともに書く>
````

ルール：
- **見出し**：`### M<番号> <伝えること> — <状態>`。見出しの状態を追えば、素材の進み具合が分かる。
  - 番号は、素材の項目を作った順に付け、付け直さない。作業履歴やスライドから、番号で指すためである。
  - 伝えることは、スライドのタイトルの案として、名詞で終える（`docs/rules/slides.md` の「文言」）。
- **状態**：次のどれかにする。
  - 候補：main が出した案で、作るかがまだ決まっていない
  - 依頼：ユーザーが作ると決めた。直しを頼んだ素材も、直し終えるまでこの状態に戻す
  - 作成済み：用意し終え、main が確かめた。ユーザーはまだ見ていない
  - 確認済み：ユーザーが見た（直しがあれば、直した後）
  - 見送り：ユーザーが作らないと決めた。本文に、そう決めたことを1行書く
- **示すこと**：図や表から読み取れる事実を先に書き、解釈はその後に書く。推測は「〜と思われる」と書く。数値は、出典と同じ桁で写す。
- **図と作り方の表**：1つの図を1行にする（写真だけの図と点を重ねた図のように、2枚で1つの素材になることがある）。
  - 図は png のパスを書く。fig は、同じフォルダに同じ名前で置く。
  - 図はこのフォルダの外にあるので、相対リンクにせず、リポジトリのルートからのパスをバッククォートで書く（上の「リンクの書き方」）。
  - 作り方は、次のどちらかで書く。
    - (a) 作った図は、スクリプト、実行した日、読んだデータを書く。
    - (b) 作業用の出力先（今は `results/<MMDD>/`）から写した図は、写した元のパス、元のスクリプト、元の実行日を書く。写してよい条件は `docs/rules/figures.md` の「置き場所と用途」にある。
- **表の素材**：図と作り方の表の代わりに、数値の表を Markdown で置き、すぐ下に出典（どのファイルのどの章か）を書く。
- **スライドでの使い方**
  - 図の上の説明の案は、`docs/rules/slides.md` の「文言」に沿って書く。「左：」「右：」は、スライドでの配置で決まるので付けない。
  - 強調したい所は、言葉で書く。丸や矢印は MATLAB の図に描かず、スライドで描くためである（`docs/rules/slides.md` の「強調の図形」）。

## follow-ups.md の書き方

続きのissueの案を書くファイル。**案**は、issue の作業中に出た作業のうち、そのissueでは行わないものである。main が仕上げで書く（`docs/staged-development.md` 7章の2）。ユーザーが作ると決めたら、Claude が案を材料にしてissueの本文を書き、issueを作る（`docs/issue-guide.md` の「Claudeがissueを作るときの手順」）。

各案の見出しには、その案が今どうなっているか（**状態**）を書く。どの案がissueになり、どの案が残っているかを、このファイルを開けば分かるようにするためである。issueを作るのは、元のissueを閉じた後になることが多い。そのため、follow-ups.md は `closed/` に移した後も、案の状態だけは更新する。

### 構成

上から次の順に書く。

| 節 | 書くこと |
|---|---|
| メタデータ | `docs/rules/communication.md` の5項目（段階: 続きのissueの案、作成者: main、作成日、入力: issue #<番号> と元にした受け渡しファイル、状態: 下書き／確定）。ユーザーが案と作るタイミングを確かめたら、確定にする |
| タイトル | `# #<番号> から続くissueの案` |
| 前書き | 元のissueが何をしたかの1文と、案をissueの本文の材料にすること |
| 言葉 | 案の中で何度も使う言葉の定義（`docs/rules/writing.md`）。無ければ節ごと省く |
| 案 | 1つの案を1つの見出しにして並べる（下の「案のひな型」） |
| 参考 | issueにしないもの（確認だけの作業、採らなかった提案など）。無ければ節ごと省く |

### 案のひな型

```markdown
## 案A：<作業の内容> — 未作成

- ラベル: `feature`（ひな型のラベル。決まっていなければ候補を並べ、ユーザーが選ぶと書く）
- ゴール: <終わったときに何ができるようになっているか>
- 背景: <なぜ要るか。元のissueのどこで分かったか（受け渡しファイルの章）>
- 未決事項の候補: <issueを作るときに、ユーザーが決めること>
- 作るタイミング: <いつ作るのがよいか。ほかの案やissueとの順番>
```

ルール：
- **見出し**：`## 案<記号>：<作業の内容> — <状態>`。記号は A、B… の順に付け、付け直さない。issueの本文やほかの受け渡しファイルから、記号で指すためである。
- **状態**：次のどれかにする。issueが閉じたかどうかは書かない。GitHub で分かるので、二重に管理しないためである。
  - 未作成：issueをまだ作っていない。作るタイミングを待っている案も含む。
  - issue #<番号>：この案からissueを作った。
  - #<番号> に含めた：ほかの案から作ったissueや、すでにあるissueの一部として扱うことにした。
  - 見送り：ユーザーが、issueにしないと決めた。
- **経過**：状態を「未作成」から変えたら、その案の箇条書きの最後に「経過」の1行を足す。
  - (a) issueを作ったときは「- 経過: YYYY-MM-DD に issue #<番号> を作った。」と書く。issueの形を案から変えたときは、変えた点と理由を続けて1〜2文で書く。
  - (b) ほかのissueに含めたときは「- 経過: YYYY-MM-DD に issue #<番号> に含めた。」と書く。
  - (c) 見送ったときは「- 経過: YYYY-MM-DD に、ユーザーがissueにしないと決めた。」と書き、理由を続ける。
- **ほかのファイルから案を指すとき**（ほかのissueの follow-ups.md、plan.md、issueの本文など）は、follow-ups.md のパスと案の記号だけを書く。「まだissueになっていない」のような状態は書かない。状態は案の見出しだけで管理する。ほかの所に書くと、issueを作ったときに古くなるためである。
- **元のissueの README**：案の状態を変えても、作業履歴には書かない。follow-ups.md の「経過」の行と二重に管理しないためである。
- **状態を変えたときにコミットする場所**：follow-ups.md が今どこにあるかで決める。
  - (a) `closed/` にあるときは、`master` にコミットする。作業ブランチや worktree のセッションでは自分では変えず、master をチェックアウトしているセッションで更新が要ることをユーザーに伝える。
  - (b) まだ作業中のフォルダ（`docs/issues/<番号>-<slug>/`）にあるときは、そのissueの作業ブランチにコミットする（例：#25 の作業中に、案D から #27 を作ったとき）。

# docs/issues/ — issueごとの作業フォルダ

## 目的

1つのissueを複数の段階（計画、評価基準の作成、実装、評価 など）に分けて進めるときに、段階のあいだで受け渡すファイルを置く場所。サブエージェントは毎回会話の記憶なしで始まるので、ここに置いたファイルが段階をまたぐ唯一の引き継ぎ手段になる。作業が終わった後は、そのissueで何を検討し、どう判断し、どう解決したかの記録として残す。**`closed/<番号>-<slug>/README.md` だけを読めば、そのissueをどう解決したか、どの文書を誰がいつ書いたかが分かる**ようにする。

小さなissue（1回のセッションで終わるもの）では作らなくてよい。

サブエージェントで段階的に進めるときの全体の手順は [`../staged-development.md`](../staged-development.md) を参照。

## 構成

```
docs/issues/
├── README.md                 このファイル
├── <番号>-<slug>/            作業中のissue
│   ├── README.md             解決のまとめ、作業履歴、ファイル一覧（下の「README.md の書き方」）
│   └── ...                   各段階の成果物
└── closed/
    └── <番号>-<slug>/        closeしたissue（中身はそのまま）
```

- フォルダ名は `<issue番号>-<内容を表す短い英語スラッグ>`（例: `42-groove-tracking`）。スラッグは作業ブランチ `claude/<slug>` と揃える。
- `docs/issues/` の直下にあるフォルダ（`closed/` を除く）が、作業中のissue。
- 各段階の成果物のファイル名（計画、評価基準、評価レポート など）は、その段階を担当するエージェントの定義（`.claude/agents/`）で決める。

## 運用の流れ

1. **作る**: issueに着手するとき、作業ブランチ上で `docs/issues/<番号>-<slug>/README.md` を、下の「README.md の書き方」のひな型で作る。「解決のまとめ」は見出しと1行だけにしておく。
2. **使う**: 各段階の成果物をこのフォルダに書き、作業ブランチにコミットする。エージェントの作業やユーザーの決定のたびに、README の作業履歴に項目を足し、見出しの状態を更新する。コミットのルールは [`../git-rules.md`](../git-rules.md) に従う。
3. **閉じる**: その前に「解決のまとめ」を書く（`summarizer` エージェント。[`../staged-development.md`](../staged-development.md) 7章）。PRの最後のコミットで、フォルダを `closed/` に移す。
   ```bash
   git mv docs/issues/<番号>-<slug> docs/issues/closed/<番号>-<slug>
   ```
   PR本文に `Closes #<番号>` を書いておくと、PRのマージと同時にissueもcloseされる。フォルダはPRと一緒にmasterへマージする。

## リンクの書き方（移動でリンクが切れないようにする）

`closed/` への移動でパスが変わる（階層が1つ深くなる）ため、リンクは次のように書く。

| リンクを書く場所 | 書き方 |
|---|---|
| フォルダ内のファイル同士 | 相対パス（`./plan.md` など）。フォルダごと移動するので切れない |
| issueのコメント・PR本文 | コミットSHA付きのパーマリンク（`https://github.com/MiwaHiroki/myResearch/blob/<SHA>/docs/issues/...`）。ブランチ名入りのURLは使わない |
| フォルダの中からフォルダの外（`src/`、他のdocs など） | 相対リンクにしない（`../../staged-development.md` は `closed/` へ移すと切れる）。リポジトリのルートからのパスをバッククォートで書く（`docs/staged-development.md`、`src/extractMultiGroove.m`） |
| フォルダの外からフォルダの中 | なるべく書かない。書く場合は、移動するコミットで書き換える |

## README.md の書き方

### 構成

上から次の順に書く。

| 節 | 書く人・時期 | 役割 |
|---|---|---|
| メタデータ | main、作るとき | `docs/rules/communication.md` の5項目（段階: 準備、作成者: main、作成日、入力: issue #<番号>、状態: 作業中／完了） |
| タイトルとリンク | main、作るとき | `# #<番号> <issueのタイトル>`、issue・ブランチ・PR・手順書へのリンク |
| 解決のまとめ | summarizer が下書きし、main が確かめる。仕上げで | どう解決したか |
| 作業履歴 | main、作業のたび | 文書・作業ごとの、いつ・誰が・何をしたか／何を決めたか。段階の状態もここに書く |
| ファイル一覧 | main、ファイルができたとき | フォルダの中のファイルの索引 |

一般的な進め方は `docs/staged-development.md` へのリンクだけにし、README には書き写さない。issue固有の進め方（例：正解データはユーザーが `ginput` で作る）は、作業履歴の「準備・全体」に書く。

### ひな型

````markdown
- 段階: 準備
- 作成者: main
- 作成日: YYYY-MM-DD
- 入力: issue #<番号>
- 状態: 作業中

# #<番号> <issueのタイトル>

- issue: [#<番号> <issueのタイトル>](https://github.com/MiwaHiroki/myResearch/issues/<番号>)
- ブランチ: `claude/<slug>`
- PR: （作ったら書く）
- 進め方: `docs/staged-development.md`、受け渡しフォルダの運用: `docs/issues/README.md`

## 解決のまとめ

仕上げで書く（summarizer）。

## 作業履歴

### 準備・全体 — 完了
成果物: `README.md`（このファイル）

- YYYY-MM-DD｜main｜issue #<番号> を受け、ブランチ `claude/<slug>` と受け渡しフォルダを作る。
- YYYY-MM-DD｜ユーザー｜**決定** 確認を省く範囲：…

### 計画 — 未着手
### 評価基準 — 未着手
### 実装 — 未着手
### 評価 — 未着手
### 振り返り — 未着手
### 続きのissue — 未着手
### 解決のまとめ — 未着手
### 仕上げ（closed/ へ移動・PR） — 未着手

## ファイル一覧

- `README.md`：このファイル
````

### 解決のまとめ

作業中は見出しと「仕上げで書く（summarizer）」の1行だけを置き、仕上げで summarizer がこの節を置き換える。メインが確かめ、記録の抜けを書き足す。目安は 80〜150 行。詳細は書き写さず、受け渡しファイルの章を示して済ませる。

```markdown
## 解決のまとめ

- 書いた日: YYYY-MM-DD（summarizer が下書き、main が確認）
- 対象のコード: `<SHA>`（この時点の `claude/<slug>` の先頭。PR #<番号>）

### 1. 結論
何ができるようになったか、採った方法、評価の結果（何回目で合格か）を2〜4文で。

### 2. 問題とゴール
issue のゴールと背景を2〜3行で（issue を開かなくても分かるように）。

### 3. 採った方法
- 処理の流れ（入力 → 出力を番号付きの手順で）
- 選んだ理由と、採らなかった案（1案1行。plan.md の案の比較から）
- 主なパラメータ（表：名前・値・決めた根拠）

### 4. 変えたファイル
| 区分 | パス | 役割・要点 |
|---|---|---|
（新規・変更の一覧。リポジトリの外のもの、例：タスクのプロンプト・許可設定も含める。
公開する関数はシグネチャを1行。保存形式の変更と、今までのデータとの互換性も書く）

### 5. 計画から変わったこと
実装・評価・仕上げの途中で plan.md から変えた点と理由（差し戻しを含む）。無ければ「なし」。

### 6. 評価の結果
合否、主な数値としきい値、ユーザーの確認（目視・試聴）の結果、評価に使ったデータの場所。

### 7. 使い方
実行するもの、冒頭で設定するパラメータ、出力の場所、ルートの README の節名。
（コードでないissueは「動き方と確かめ方」）

### 8. 制約と残った課題
既知の制約。follow-ups.md の案を1行ずつ。

### 9. 詳しく読むには
各節の出典（作業履歴の項目、plan.md・criteria.md・eval-report の章、主なコミットの SHA）。
```

ルール：
- **根拠のあることだけを書く。** 受け渡しファイル・issue・差分・コードのどれにも無いことは書かず、「記録なし」とする。計画とコードが食い違えばコードを正とし、5節に書く。
- 名前とパスは、対象のコードの SHA の時点のものを書く（後でリネームされても `git show <SHA>:<パス>` でたどれる）。数値は出典と同じ桁で写す。
- 新しく出てくる記号・変数は、初出で意味を書く。
- 当てはまらない節は、見出しを残して「該当なし」と書く。
- 仕上げの後でコードが変わったら（Auto-fix など）、メインが5節に1行足し、対象のコードの SHA を書き換える。

### 作業履歴

段階の状態と決定事項・申し送りを、**文書・作業ごとに**まとめる。見出しごとに、いつ・誰が・何をしたか／何を決めたかを日付順に並べる。見出しに今の状態を書くので、見出しを追えば段階の状態が分かる。

```markdown
## 作業履歴

### 計画 — 承認済み
成果物: [`plan.md`](./plan.md)

- 2026-10-26｜planner｜`plan.md` を書く（1回目）。
- 2026-10-27｜ユーザー｜**決定** 承認。Q1〜Q4 はすべて推奨どおり（`BIN_WIDTH = 1`・`BAND_TOL = 3`）。
  - 理由や細目は、このように字下げして続ける。
- 2026-10-27｜main｜決定を `plan.md` 8章に書き、状態を「承認済み」にする。

### 実装 — 完了（1回目）
成果物: [`impl-report-1.md`](./impl-report-1.md)、コード `560e085`

- 2026-10-28｜implementer｜1回目。`runAllTests` 217件すべて通過。
- 2026-10-28｜main｜報告を確かめ、実装をコミットする。
```

ルール：
- **見出し**：`### <作業> — <状態>`。作業は次の順に並べる：準備・全体、計画、評価基準、実装、評価、振り返り、続きのissue、解決のまとめ、仕上げ（closed/ へ移動・PR）。issue固有の作業（例：ユーザーが行う正解データの作成、リポジトリの外への反映）は、行われる位置に足す。番号は振らない（足したときに振り直さなくてよいように）。
- **状態**：未着手／作業中／下書き／承認済み／完了／合格（n回目）／不合格（n回目）。
- **成果物の行**：見出しの直後に、その作業で書いたもの。フォルダの中は相対リンク、外はバッククォートのパス、コードはコミットの SHA。
- **項目**：`- YYYY-MM-DD｜<担当>｜<内容>`。担当はエージェント名（evaluator は `evaluator（A）`・`evaluator（B）` とモードも）、`main`、`ユーザー`。同じ見出しの中は日付順。
- **決定**：ユーザーやメインが決めたことは、内容の頭に **決定** を付ける（`決定` で検索すれば一覧できる）。決定は、それが**効く作業**の見出しの下に書く（例：実装の後に評価の日付を決めたら「評価」の下）。全体に効くもの（確認を省く範囲など）は「準備・全体」の下に書く。
- **差し戻し**：実装・評価の2回目以降は、同じ見出しの下に「（2回目）」として続ける。
- **長い記録**（調べたことのメモなど）は、フォルダの中の別のファイル（例：`notes.md`）に分け、項目からリンクする。

### ファイル一覧

フォルダの中のファイルを、相対リンクと内容の1行で並べる。作者・日付・状態は作業履歴に書くので、ここには書かない（二重に管理しないため）。フォルダの外のもの（受け入れテスト、評価スクリプト、コード）は、作業履歴の成果物の行に書く。

```markdown
## ファイル一覧

- `README.md`：このファイル
- [`plan.md`](./plan.md)：計画
- [`criteria.md`](./criteria.md)：評価基準
- [`impl-report-1.md`](./impl-report-1.md)：実装の報告（1回目）
```

### 1. 結論

自動追跡の3つのスクリプト（`scripts/grooveTrack_1cycle.m`・`scripts/grooveHist_Ncycle.m`・`scripts/grooveTrack_Ncycle.m`）で、溝底区間（暗さがしきい値以上の行が続く範囲）の幅の上限を 8 から 4\[px\](`WIDTH_THRESH`) に下げ、幅の広い区間から溝底点を作らないようにした。正規化した振幅が1付近になる外れ値は、溝底の暗い線に溝の斜面と考えられる薄暗い行がつながって区間が広がり、重心が 1〜2 px ずれた溝底点だったためである。保存したクリック位置で作り直すと、外れ値（前後21列の中央値から 1 px を超えてずれた点）は、1周分で 1 → 0、5周分の本実装で 26 → 0、5周分の正解データで 25 → 0 になり、幅4以下の点を採っていた列は1列も変わらなかった。評価は**1回目で合格**した（2026-11-20。計画の書き直しが1回、実装の差し戻しは0回）。

### 2. 問題とゴール

#30 の評価で、正規化した振幅が1付近になる外れ値（前後の列から 1〜2 px 跳んだ溝底点で、クリックのような音になる）が、5周分の本実装にも正解データにも見つかった。issue を作る前に確かめると、外れ値は溝の選び方（自動追跡、ヒストグラムの帯、従来法の帯）によらず同じ点に出ており、#30 の続きの案だった自動追跡（`trackGroove`）のパラメータの調整では減らなかった。そこでこのissueでは、外れ値がどの段階で生じるかを確かめてから直し方を決め、1周分（1014 のデータ）と5周分（1104 のデータ）の両方で外れ値を減らすことをゴールとした。外れ値でない点（音の成分）を変えないこと、`experiments/` に新しいデータを作らないこと、従来法の出力を変えるならユーザーの承認を得ることが条件である。

### 3. 採った方法

#### 言葉

- **溝底区間**：写真の各列で、暗さ（1 − 画素値/255）がしきい値 0.6(`D_THRESH`) 以上の行が続く範囲。
- **幅**：溝底区間の最後の行 − 最初の行 [px]。3行の区間なら幅2である。
- **溝底点**：溝底区間ごとに1つ求める y 座標。
- **重心法・局所的最大値法**：溝底点の求め方。重心法は区間の行を暗さで重み付けして平均し、局所的最大値法は区間の中で最も暗い行を選ぶ。
- **溝の選択**：写真1枚分の溝底点から、1本の溝の点を列ごとに1つ選ぶこと。点を選べなかった列は、前後の列から補間する。
- **振幅**：選んだ溝の y から写真ごとに9次の多項式を引いて再生順につなぎ、全体の平均を引いて 1.5\[px\](`AMP_DIV`) で割った値。wav に書く値で、絶対値が1を超えた所は切り捨てられる。
- **局所的なずれ**：選んだ点のデトレンド前の y から、前後10列（合わせて21列）のうち点を採れた列の y の中央値を引いた値。
- **外れ値**：局所的なずれの絶対値が 1 px を超える点（このissueでの定義）。
- **幅の広い点**：選んだ点のうち、幅が5以上のもの。
- **t1014・h1104・t1104**：比べた3つの保存済みのデータ。t1014 は1周分の自動追跡（#25）、h1104 は5周分の本実装（#30。1本目を追跡し、2〜5本目をヒストグラムの帯で取り出す）、t1104 は5周分の正解データ（#30。5本ともクリックして追跡）である。
- **直す前・直した後**：幅の上限を 8・4 にして、保存したクリック位置から、溝底点の検出・溝の選択・デトレンドをやり直した結果。
- **変わった列**：直す前と後で、デトレンド前の y が変わった列（差が 1e-9 を超える列）。

#### 考え方

外れ値は、溝の選び方ではなく、溝底点を検出する段階で生じていた。写真では、溝底の暗い線のすぐ隣に、暗さがしきい値すれすれの行が続いていることがある。ユーザーは、ここを溝の斜面と考えられる所と判断した。この行がしきい値をわずかに上回ると、溝底区間がそこまでつながり、幅が5以上になる。重心法では、すれすれの行も溝底の行とほぼ同じ重みで効くので、区間が片側に1行広がるごとに、点がその側へ約 0.45 px ずれる。issue の発端の 715 ms の跳び（1014、写真8、x=1862）では、溝底の線の下の3行（暗さ 0.608・0.605・0.620）が区間に入って幅6になり、点が隣の列より約 1.4 px 下にずれていた。溝の選択は、追跡も帯も許す範囲（2〜3 px）がこのずれより広いので、ずれた点をそのまま採っていた。

ずれた点は、幅で見分けられる。h1104 で選んだ 160,413点のうち、幅の広い点は104点（0.06%）しかないが、外れ値の26点はすべてその中にあった。幅4以下の点の局所的なずれは、最大 0.967 px で、1 px を超えない。そこで、幅の広い区間をそもそも溝底点にしないことにした。その列ではその溝の点が無くなるので、溝の選択が前後の列から補間する。幅4以下の点は1つも変わらない。

代わりに、幅が広くても外れ値ではなかった点（h1104 で78点）も、補間に置き換わる。その中には、区間が上下に同じだけ広がって、点が正しく溝底の上にあったものもある。ユーザーは、暗さのしきい値で溝底を決めるこの方法では避けられないとして受け入れ、欠点として明記することにした。なお、局所的最大値法は区間の中で最も暗い行を選ぶので、区間が広がってもほとんどずれない。それでも、2つの手法の溝底点を同じ溝底区間から作るため、同じ上限を使う。

#### 処理の流れ

自動追跡の3つのスクリプトの処理の流れは変えず、手順2の (2) で使う幅の上限だけを 8 から 4 にした。写真（8枚）ごとに、次の手順を行う。

1. 写真を横に10等分した区間（セグメント）ごとに、`omitMask` で端の無効な所を除き、`DarknessMap` で暗さの行列を作る。`setDiffTF` で、暗さが 0.6(`D_THRESH`) 以上になる所の始まりと終わりを求める。
2. セグメントの列ごとに、`GrooveExtractor` で溝底点を求める。
   - (1) `findThresholdIntervals` で、暗さがしきい値以上の行が続く範囲をすべて求める。
   - (2) `findGrooveBottomIntervals` で、幅が 4\[px\](`WIDTH_THRESH`) 以下の範囲だけを溝底区間として残す（**変えた所**。前は 8）。上限に `scaleFactor.row`（高解像度化の縦の倍率）を掛けて比べるので、上限は元の画像の px で書く。
   - (3) `extractByCentroid`（重心法）と `extractByLocalMax`（局所的最大値法）で、残った区間ごとに溝底点を求め、`GroovePointCloud` に入れる。
3. `mergeSegmentPoints` で、10セグメントの溝底点をつなぎ、写真1枚分の点群と列の座標を得る。
4. 溝を選ぶ（変えていない）。幅の広い区間を捨てた列では、その溝の点が無いので、点を採らずに前後の列から補間する。
   - (a) `grooveTrack_1cycle.m` は1本、`grooveTrack_Ncycle.m` は写真ごとにクリックした N 本（`NUM_GROOVES`。評価では5）を、それぞれ `trackGroove` で追跡する。列ごとに、予測した位置から 2\[px\](`TRACK_TOL`) 以内の最も近い点を採る。
   - (b) `grooveHist_Ncycle.m` は、`extractMultiGroove` で1本目を同じように追跡し、2本目以降は y のヒストグラムの山から ±3\[px\](`BAND_TOL`) の帯の点を採る。
5. `detrendTrackedShape` で写真ごとに9次の多項式を引き、振幅にして wav と cycleResult（`saveCycleResult` で保存する結果の .mat）を作る（変えていない）。cycleResult の `conditions.wTh` には 4 が入る。

`findGrooveBottomIntervals` は、幅が上限以下の区間を、順番を変えずに残すだけである。そのため、上限4で検出した溝底点は、上限8の溝底点から幅の広い点を除いたものと、並びも含めて一致する（評価の R2）。h1104 では、ヒストグラムの山の中心も変わらない。

#### 選んだ理由と、採らなかった案

- 直す段階と方法（plan.md 3章）。数値は h1104 の重心法の、外れ値の数、振幅の絶対値が 0.8・1 を超えるサンプルの数、変わった列の数で、直す前は 26・56・32 である。
  - 採った案A は、検出の段階で、幅5以上の区間を溝底点にしない。0・9・0・106列（幅4以下の点の列は0）で、原因に直接効き、変える所が最も少ない。
  - 採らなかった案
    - 案A' は、幅を点と一緒に持ち、溝を選んだ後で幅の広い点を除く。結果は案A と完全に同じだが、`GroovePointCloud` や `mergeSegmentPoints` の出力を変える必要があり、変える所が多い。
    - 案B は、溝を選んだ後で、局所的なずれが 1 px を超える点を除いて補間する。2・32・17・28列で、続いた外れ（写真5の4本目の17列）と、ずれ 0.85〜0.95 px の点を見逃す。ほかのレコードで、音の鋭い部分を誤って除くおそれもある。
    - 案C は、`trackGroove` の `Tolerance`・`FitLength` を変える。1014 で追跡の許す範囲を 1.0\[px\](`Tolerance`) にすると、振幅の絶対値が 0.8 を超えるサンプルが 2 → 22 に増える。帯で取り出す2本目以降には効かない。
    - 案D は、幅の広い区間だけ、最も暗い行の上下2行で重心を計算し直す。0・21・0・104列で、新しい計算方法を足すわりに約 0.45 px のずれが残る。写真5の4本目の続いた幅の広い点を溝の形として残せるが、ユーザーはそこを溝の本当の形ではない（針が溝の斜面を削った所の影）と判断した（Q7）。
  - 案E（すべての点で、重心の重みを「暗さ − しきい値」にする）は、続きの案として残した。幅4以下の点で区間がまるごと1行ずれる 0.9 px の跳びも消える（ずれが 0.75 px を超える幅4以下の点が 193 → 0）。ただし、重心法の定義が変わってすべての点が変わり、外れ値も2点残る。ユーザーは効果がありそうだと考えており、あとで詳しく検討する。
- 作り方
  - 3つのスクリプトの `WIDTH_THRESH` の値だけを変えた。1回目の計画は、検出の処理を新しい関数 `src/detectGroovePoints.m` にまとめることを推奨した。ユーザーはリファクタリングを別の機会にまとめて行うので、本実装と直接関係のない共通関数は作らないと決めた。2回目の計画で、スクリプトの値を変えるだけでも、1回目の計画の試行と同じ結果になることを確かめた。
- 変える範囲
  - 自動追跡の3つのスクリプトだけを変え、従来法（`fitGroove` で溝を選ぶ `pkCentroid_1cycle.m` など）は 8 のままにした（Q5）。従来法は過去と同じ結果を作り続け、比べる基準として残る。高解像度化した画像での幅の分布も、まだ確かめていない。
  - 局所的最大値法にも同じ上限を使う（Q6）。2つの手法を同じ溝底区間で比べられるようにするためである。h1104 では局所的最大値法の33列が変わる（y の変化の中央値 0.30 px、最大 0.88 px）。
- 外れ値の定義（Q1）
  - 局所的なずれ（21列の窓）の絶対値が 1 px を超える点を、外れ値とした。正解データも本実装と同じ追跡を含むので、正解に依らない列ごとの指標にした。窓を11列にすると、5列続いた外れ値を見逃す。61列以上にすると、音のゆっくりした揺れが入り、幅4以下の点まで数える（61列で40点、101列で414点）。21列は、すべての外れ値を数え、幅4以下の点を数えない最も短い窓である。
  - 採らなかった定義
    - 振幅の絶対値が 0.8 や 1 を超えるサンプルは、音の大きい所（幅4以下の点で9か所）も数え、デトレンドでも変わる。参考として数えた。
    - 従来法との同じ x での y の差（ユーザーの最初の案）は、従来法のデータが 1014 の1本目にしか無く、両方が同じ外れ値を採った所は差に出ない。
  - 11列以上続く外れ値を数える指標（芯からのずれが続く区間、Q9）は、別の機会に回した。提案が複雑で、すぐに直すべき重大な欠点でもないためである。このissueでは、直す前の幅の広い点が続く区間で場所を一覧し、図で確かめた。

  - 評価スクリプト（939行）のコードは、誰もレビューしていない（retrospective.md 6章）。

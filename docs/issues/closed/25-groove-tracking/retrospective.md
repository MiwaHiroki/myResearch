# #25 サブエージェントによる段階的な開発の試験運用 — 振り返り

## 1. 結論

- **計画 → 評価基準 → 実装 → 評価の4段階を、専用のサブエージェントで最後まで進められた。** 実装は1回目で評価に合格し、差し戻しは0回だった。
- 一番効いたのは、**plannerが実データで案を確かめたこと**と、**段階の区切りでユーザーが確認したこと**。前者は参考ブランチのDPの欠点と正解データの再現性の問題を実装の前に見つけ、後者はユーザーにしか分からない知識（マスクの位置、パラメータの単位、データを作り直すべきこと）を計画に入れた。
- 一方で、**運用の約束ごと（ブランチ、日付、作業ツリーの状態、受け渡しの書き方）**で小さな問題が続いた。どれもルールや定義を足せば防げるものなので、7章に改善案をまとめた。

## 3. うまくいったこと

- **plannerが実データで案を確かめた。** 参考ブランチのDPが列の40〜80%を飛ばすことや、正解データ（`origD_0731`）が `ad46b44` の後のコードでは再現できないことを、計画の段階で見つけた。後者は評価の設計を大きく変えた。
- **ユーザーの確認を挟む場所が効いた。** 計画のレビューで、マスクは写真の両端にしか無いこと、パラメータは列数でなくpxにすべきこと、`ad46b44` 以降1周分のデータを作っていないことが入った。
- **エージェントがルールや基準の誤りを見つけた。** plannerは `data.md` の `saveCycleResult(Overwrite=false)` の記述の誤りを、evaluatorは `criteria.md` の差分の基準コミットの誤りを指摘した。
- **評価基準を実装の前に固められた。** 受け入れテストは、計画どおりの試作で全件通ること、わざと誤らせた試作2種で狙ったテストが落ちることで確かめてあった。
- **実装が計画どおりに進んだ。** 出力の数値は計画の試行と一致した。implementerは、`date` の書き換え忘れでエラーにするなど、上書きを防ぐ工夫を自分で足した。
- **書き込み範囲の制限が守られた。** どの段階でも、範囲外のファイルの変更は無かった（メインが `git status`・`git diff` で確認）。
- **依頼文に手順の順番と理由を書くと、そのとおりに動いた。** 評価（モードB）では、作業ツリーをきれいに保つ順番（データを作り終えるまで追跡されるファイルを作らない）と、`temp/` の使い方を依頼文に書き、`gitDirty = 0` のデータが作れた。

## 5. 中間版で「評価の後に確かめる」とした項目の結論

- **しきい値の余裕（4章の7）**：今回は通ったが、余裕0.022pxの項目は、実装の細部（同点のときの選び方など）が試作と違うだけで落ちうる。試作の再現を確かめるしきい値と、品質の基準を分けて書くべき（7章 A4）。
- **評価担当の試作の重複（4章の8）**：受け入れテストの確かさを上げる効果は大きかった（誤らせた試作で狙ったテストが落ちることを確かめられた）。ただし、試作を毎回まるごと作る必要はない。複雑な関数に絞る、または計画の付録の試行コードを流用する（7章 A4）。
- **受け渡しファイルの長さ（4章の9）**：問題は起きなかった。今のままでよい。

## 6. 今後検討したいこと

- **コードレビューの段階を足す。** 評価担当が確かめるのは動作と数値で、コードの読みやすさや `docs/rules/coding.md` を守っているかは見ていない。実装の後、評価の前（または並行）に、`/code-review` などで作業ブランチの差分をレビューする段階を足すことを考える。今回は時間の都合で行わなかった（2026-10-13、ユーザー）。
- **進め方の手順書を作る。** 段階の流れ、各エージェントの呼び方（依頼文の型）、確認を挟む場所、上の2・3・6・10・11・12の運用をまとめる。
- **続きのissue。** [`follow-ups.md`](./follow-ups.md) にメモした。

## 7. ルール・エージェント定義の改善案

### 7.1 決定（2026-10-19、ユーザー）

- **A1〜A4：採用。** masterで、ルールとエージェント定義に反映する（反映したコミットはgitの履歴と受け渡しフォルダの `README.md` に残す）。
- **A5：タスクの内容を変えて対応する。** 進捗ログのスケジュールタスクが、チェックアウト中のブランチではなく常にmasterにコミットするように変える（[`follow-ups.md`](./follow-ups.md) の案D。別のissueにする）。それまでは、手順書に「作業ブランチをチェックアウトしている間は、進捗ログの自動コミットがそのブランチに入る」と書いて対応する。

### 7.2 改善案の一覧

| ID | 対象 | 案 | 関係する問題 |
|---|---|---|---|
| A1 | `docs/rules/data.md` | `experiments/` に保存する実データの実行は、**作業ツリーがきれいな状態（すべてコミットした後）**で行う。日付や `PREV_RESULT_PATH` を書き換えたスクリプトのコピーは、スクラッチパッドではなくプロジェクトの `temp/`（gitの管理外。ユーザーも見られる）に置く | 4章の6 |
| A2 | `planner.md`・`implementer.md` | 正式なデータ（`experiments/` に残すもの）の作成は、計画で**評価の段階に割り当てる**。実装担当の実データでの動作確認は、`experiments/` に保存しない（`results/` の図や数値の表示だけにする） | 4章の6 |
| A3 | `evaluator.md`（モードA）、手順書 | 差分の基準は「受け入れテストを追加したコミット」と書き、ハッシュはメインがコミットしたときに埋める | 4章の11 |
| A4 | `evaluator.md`（モードA） | `criteria.md` のしきい値を、「計画どおりに実装したかの確認」（試作の結果が根拠）と「品質の基準」（基準データの再現性などが根拠）に分けて書く。受け入れテストを確かめるための試作は、必要な関数に絞り、計画の付録の試行コードがあれば流用する | 4章の7・8 |
| A5 | スケジュールタスク `progress-report-daily`、手順書 | タスクが常にmasterにコミットするように変える（別のissue、`follow-ups.md` の案D）。それまでは手順書に注意として書く | 4章の12 |

## 言葉

## 1. 結論

- **計画・評価基準・実装・評価のどれも、書き直しと差し戻しが0回で終わった。** 評価は1回目で合格した（2026-11-26、ユーザーが U1〜U3 を確認）。

- 一番効いたのは、**移行を「試し → 承認 → 実行 → もう一度試し」の順にしたこと**である。移す前の817ファイルの SHA-256 を評価基準の段階で記録したので、移した後に1つも失われていないことを数で確かめられた（817/817）。

## 3. うまくいったこと

- **移行を、対応表の CSV と1つの関数で行った。** 手で移すと起きやすい移し忘れと打ち間違いを避けられた。関数は、全部の行を先に確かめ、1つでも問題があれば何も動かさない。上書きもしない。試しの表を承認B でそのまま見せられたので、ユーザーは移し先を1行ずつ確かめられた。
- **データの保全を数で確かめた。** 評価基準の段階で、移す前の817ファイルのパス・大きさ・SHA-256 を記録した。評価では、移した後の817ファイルがすべて同じ中身であること、`experiments/` の15ファイルが同じ中身であることを確かめた。
- **書き換えで数値が変わらないことを、実データで2回確かめた。** 実装担当と評価担当が、それぞれ 1014 の手動選択を再現し、溝形状が保存した結果と `isequal` になった。0924 のバイラテラルフィルタの wav も、まったく同じになった。
- **承認を3つに分け、それぞれの直前に見せた。** README の表（承認A）は実装の前半の直後に、移し先（承認B）は移す直前に、バックアップ（承認C）は改名の直前に確かめた。改名から評価までを同じ日に行い、master のスクリプトで `experiments/` を読めない期間を短くした。
- **計画どおりに数が合った。** 計画の見込み（603・55・52・92・144 など）は、評価基準・実装・移行・評価のどの段階でも同じだった。
- **利用上限で止まった評価担当を、同じエージェントの再開で仕上げた。** 作り終えたファイルを伝えて SendMessage で再開し、作業をやり直さずに済んだ。

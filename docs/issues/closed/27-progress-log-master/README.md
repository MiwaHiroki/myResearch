### 1. 結論

進捗ログ（`docs/progress/` の期間ファイル。数週間ごとの進捗報告に使う日々の記録）を毎日3時に自動で書くスケジュールタスク `progress-report-daily` が、どのブランチをチェックアウトしていても、masterの履歴を読み、masterにコミットするようになった。作業ブランチにいる日は、まずブランチを切り替えずにmasterの状態を読む。書き込みが要る日だけ、一時的にmasterへ切り替えてコミットし、元のブランチに戻る。追跡されているファイルに未コミットの変更があれば切り替えず、その日は見送って通知する。変えたのは、リポジトリの外にあるタスクのプロンプトと許可設定（ルール16件の追加）と、関係する手順書3つである。評価は**1回目で合格**した（2026-10-23、差し戻し0回）。リポジトリの写し（砂場）で、本番と同じ許可設定のままプロンプトを20回実行させる予行で、すべての項目を満たした。

### 2. 問題とゴール

旧タスクは、チェックアウト中のブランチ（`HEAD`）を基準に新しいコミットを読み、そのブランチにコミットしていた。そのため #25 の作業中は進捗ログのコミットが作業ブランチに入り、PR #26 のマージ後も4件がマージ済みのブランチに取り残された。状態ファイル `docs/progress/.state.json` の `last_commit`（前回どこまで読んだかを示すコミット）も作業ブランチ側を指し、手で直した（`ba9077d`）。ゴールは、進捗ログのコミットを常にmasterに入れ、`last_commit` が常にmasterの履歴を指すようにすることである。深夜の無人実行で承認待ちに止まらないこと、ユーザーの未コミットの変更を壊さない・混ぜないこと、pushせず `docs/progress/` 以外をコミットしないことも条件とした。

### 3. 採った方法

#### 考え方

タスクの実体は、プロンプト（`~/.claude/scheduled-tasks/progress-report-daily/SKILL.md`）に従って動く Claude のセッションである。Claude のアプリが、メインのチェックアウト（リポジトリのルートの作業ツリー。別に作る worktree ではないほう）で毎日3時に実行する。人が承認できない時間に動くので、gitコマンドが1つでも許可ルールに一致しないと、承認待ちで止まる。そこで、使ってよいgitコマンドを16の決まった形（読み取り9、書き込み7）に限ってプロンプトに一覧で書き、今のルールでは許されない形のために、許可ルールを8つ足した。1回の呼び出しには1コマンドだけを書き、`&&`・`;`・`|` でつながず、`-C` も付けない。つないだコマンドは1つずつ照合され、`-C` が付くとルールに一致しないためである。

ブランチの切り替えは、ユーザーや並行して作業するセッション、開いている MATLAB に影響しうるので、できるだけ減らす。そのため、まずブランチを切り替えずに、masterにコミットされた状態ファイルとmasterの履歴を `git show`・`git log` で読み、その日に書くことがあるかを決める。書くことがある日だけ、masterへ切り替える。旧タスクでは、前回のタスク自身のコミットが毎回「新しいコミット」になり、何もしない日がほとんど無かった（10-14〜10-20 の日次ログは、ほぼその1行だけだった）。そこで、タスク自身のコミットは日次ログに載せず、書くことにも数えない。

切り替えるときのために、次の3つの安全の仕組みを入れた。
- 切り替える前に、元のブランチ名をgitの設定のキー `progress-report.return-branch` に記録し、戻ったら消す。途中で止まっても、次の実行で気づける。
- コミットの末尾に `-- docs/progress/` を付け、`docs/progress/` だけをコミットする。ユーザーがステージした変更を混ぜない。
- `last_commit` が、masterの first-parent の履歴（マージでは第1親だけをたどる、master自身が進んできた履歴）の上にあることを毎回確かめる。外れていると読む範囲がずれて二重に追記するので、何も変えずに知らせる。

#### 処理の流れ

新しいプロンプト（[`skill-after.md`](./skill-after.md)）は、次の手順1〜5で動く。通知はアプリの通知（`PushNotification`。日本語1行、200字以内）で送る。種類は、見送り（N1）、前回の中断（N2）、元のブランチに戻れない（N3）、`last_commit` の異常（N4）、そのほかの異常（N5）と、次回の進捗報告の予定日の質問である。

1. 手順1で、状況を確かめる（何も変えない）。
   - (1) 記録のキー `progress-report.return-branch` を読む（無ければ `none`）。
   - (2) チェックアウト中のブランチを読む。masterなら `master`、作業ブランチならその名前、detached HEAD（ブランチではなくコミットを直接チェックアウトした状態）なら `HEAD` が出る。
   - (3) 記録が残っていれば、前回の実行は途中で止まっている。
     - (a) 今がmasterなら、切り替えた後に止まったので、N2 を送って何もせずに終わる。
     - (b) 今がmasterでなければ、戻った後に止まっただけなので、記録を消して続ける。
2. 手順2で、masterの状態を読み、今日やることを決める（ブランチは切り替えない）。
   - (1) `git show master:docs/progress/.state.json` で、masterにコミットされた状態ファイルを読む。作業ブランチの `docs/progress/` は古いことがあるので読まない。読めないか壊れていれば、N5 を送って終わる。
   - (2) `git merge-base` で、`last_commit` がmasterの祖先であることを確かめる。
   - (3) `last_commit` からmasterの先端までの first-parent の履歴を、古い順に読む。最初のコミットの第1親が `last_commit` と一致することを確かめる。(2)・(3) のどちらかが外れたら、N4 を送って終わる。
   - (4) タスク自身のコミット（件名が「進捗ログ自動更新（」か「進捗期間を区切り、新しい期間ファイルを開始（」で始まるもの）を除く。マージは、マージされたブランチの側のコミット（第1親から第2親までの範囲）を中身として読み、中身のマージとタスク自身のコミットも除く。中身が空になれば、そのマージも除く。残りが「載せるコミット」である。
   - (5) やることがあるのは、載せるコミットがある日、次回の進捗報告の予定日を過ぎた日（期間の区切り）、予定日が未定で最後に尋ねてから3日以上たった日（予定日の質問）、masterにいて前回の書きかけが `docs/progress/` に残っている日の4つである。どれにも当たらなければ、切り替えず、通知もせずに終わる。
3. 手順3で、チェックアウト中のブランチに応じて、作業する場所を用意する。
   - (a) detached HEAD なら、N1 を送って終わる。
   - (b) masterなら、マージや cherry-pick の途中のときだけ N1 で見送る。`docs/progress/` の外に未コミットの変更があっても続ける（コミットを `docs/progress/` に限るので混ざらない）。前回の書きかけが残っていれば、矛盾が無いことを確かめて今回の分に含める。
   - (c) 作業ブランチなら、`git status --porcelain --untracked-files=no` で、追跡されているファイルに未コミットの変更が無いかを調べる。あれば切り替えずに N1 を送って終わる。無ければ、元のブランチ名を記録してから `git switch master` で切り替える。追跡されていないファイルだけなら切り替えてよい（上書きになる場合は、`git switch` が何も変えずに失敗するため）。切り替えに失敗したら、記録を消して N1 を送って終わる。
4. 手順4で、進捗ログを書き、masterにコミットする。
   - (1) 状態ファイルと期間ファイルを読み直す。切り替えた後は中身が変わっているためである。状態ファイルが手順2で読んだものと違えば、N5 を送って手順5へ進む。
   - (2) 載せるコミットを日次ログに追記し、「まとめ」の節を日次ログ全体から作り直す（書き方は下の「日次ログの書き方」）。
   - (3) この実行の最初のコミットの前に一度だけ、状態ファイルの `last_commit` を、コミットする前のmasterの先端（`git rev-parse master`）にする。
   - (4) 触ったファイルを `git add` で追加し、末尾に `-- docs/progress/` を付けた `git commit` でコミットする。本文には、チェックアウト中だったブランチの名前を書く。
   - (5) 期間の区切りと予定日の質問は、旧プロンプトの手順7のとおりに行う。予定日の質問だけをした日は、件名を「進捗ログ自動更新（その日の日付、通知の記録）」の形にして、質問した日の記録をコミットする。日次ログを書いた日なら、これは2件目のコミットになる。
5. 手順5で、元のブランチに戻す（手順3で切り替えたときだけ。手順4の途中で失敗したときも行う）。
   - (1) `docs/progress/` にコミットされていない変更が無いことを確かめる。あれば戻らずに N3 を送って終わる（記録は残す）。
   - (2) `git switch -` で直前のブランチに戻る。並行のセッションの変更は、gitが元のブランチへ持ち帰る。
   - (3) 戻った先が記録したブランチであることを確かめて、記録を消す。違えば、記録を残したまま N3 を送る。

日次ログの書き方も変えた。
- タスク自身のコミットは書かない。
- PR のマージは、「PR #NNをmerge（要約、Nコミット、MM-DD〜MM-DD）」という親の行の下に、中身のコミットを1件1行の子の行で、元の日付を添えて書く。作業ブランチの途中経過はマージの後にしか載らないので、中身のコミットも残す。GitHub のmasterを `git pull` で取り込んだマージは、「GitHubのmasterを取り込み（PR #NN を含む、Nコミット）」と書く。
- 見出し（`### YYYY-MM-DD`）の日付は、末尾の見出しより前に戻さない。同じ日付なら末尾の見出しの下に続けて書く。cherry-pick などで入った古い日付のコミットは、末尾の見出しの下に「（MM-DDのコミット）」を添えて書く。こうして、見出しは日付順に並び、同じ日付の見出しは2つできない。

#### 選んだ理由と、採らなかった案

issue の未決事項 Q1・Q2 と、計画の未決事項 Q1〜Q9 は、ユーザーの指示（「今回は私の承認を求めず、自律的に実装を進めてください」）により、すべて推奨どおりに main が決めた（2026-10-22。この README の「決定事項・申し送り」、plan.md 8章）。
- 採用（issue の Q1 (a)）：作業ブランチにいるときは、一時的にmasterへ切り替えて戻す。不採用の (b) 進捗ログ専用の worktree でmasterを扱う案は、メインのチェックアウトでmasterに切り替えられなくなる。(c) masterでないときは何もしない案は、作業ブランチにいる間ずっと進捗ログが止まる。
- 採用（issue の Q2 (a)）：載せるのはmasterの履歴だけ。不採用の (b) 作業ブランチのコミットも載せる案は、マージされなかった作業も載り、記録が複雑になる。
- 採用（plan.md の案B）：切り替えずに読み、書き込みが要る日だけ切り替える。不採用の案A（毎回切り替える）は、作業ブランチにいる間ほぼ毎日切り替え、`last_commit` の異常にも切り替えた後でしか気づけない。案C（追記する行まで切り替えの前に作る）は、切り替えの前後のファイルを取り違える危険があるので、「下書きを作っておいてよい」の一文だけを取り込んだ。gitの低水準のコマンドでチェックアウトに触れずにコミットする案は、コマンドの形が多く、LLM が正確に組み立てるのが難しい。
- タスク自身のコミットを載せない（計画の Q1）。載せ続けると、作業ブランチにいる間はほぼ毎日切り替えることになり、案Bの利点が無くなる。
- 戻り方は `git switch -` にした。`git switch @{-1}` は PowerShell で `@{` が壊れる。`git switch <ブランチ名>` は `git switch *` のルールが要り、`-c`・`-f` などの形も許してしまう。`git switch -` が完全一致のルールに一致するかは公式の文書に無かったので、予行で確かめた（一致した。plan.md 9章の R1）。
- 中断の記録は gitの設定に置く（計画の Q5）。`temp/` に印のファイルを置く案は Write のルールが増え、reflog から推測する案はユーザーの切り替えと区別できない。
- masterで `docs/progress/` の外に変更があっても続ける（計画の Q3）。見送る案だと、masterで作業したまま夜を越すたびに進捗ログが止まる。作業ブランチで追跡されていないファイルだけのときも切り替える（Q4）。見送る案だと、消えないファイルが1つあるだけで、ずっと見送りになる。
- 日中の追いつきの実行や手動の実行でも切り替える（計画の Q7）。0〜6時以外は切り替えない案は、時刻を得るコマンドが増え、手動での確かめもできなくなる。
- 検証は、砂場でのヘッドレスの `claude -p` で行う（計画の Q8 (a)）。評価担当が手でプロンプトをなぞる案では、許可ルールとの照合を確かめられない。

### 5. 計画から変わったこと

### 7. 動き方と確かめ方

この節は、対象のコードの時点（2026-10-23 の反映）の動き方である。2026-11-11 からの変更は8節に書いた。
1. ふだんは何もしなくてよい。タスクは、Claude のアプリが起動していて PC が起きているとき、毎日3時にメインのチェックアウトで動く。スリープ中に時刻が過ぎたら、起きた後に1回だけ追いついて動く（plan.md 2.2）。

3. 作業ブランチで夜を越した翌朝に、次の4つで動きを確かめられる（follow-ups.md の1）。書き込みが要らない日は、切り替えずに終わるのが正しい動きである。

   - (2) `git log --oneline master..<作業ブランチ>` で、作業ブランチに進捗ログのコミットが無いことを見る。
   - (3) `git rev-parse --abbrev-ref HEAD` で、チェックアウトが作業ブランチのままであることを見る。
   - (4) `git config --get --default none progress-report.return-branch` が `none` であることを見る。
4. 通知が来たら、種類に応じて対応する。
   - (a) N1（見送り）のときは、変更をコミットすれば、次に書き込みが要る日に書かれる。
   - (b) N2（前回の中断）のときは、チェックアウトを確かめて元のブランチに戻し、通知の文の案内どおり `git config --unset progress-report.return-branch` で記録を消す。N3（元のブランチに戻れない）のときも、チェックアウトがmasterのままなので、確かめて元のブランチに戻す。

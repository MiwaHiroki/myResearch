# #27 続きの確認・課題の案

## 1. (iv) 作業ブランチでの本物の実行（確認だけ。issueにはしない）

予行（砂場の `claude -p`）では全場面が合格したが、本物のアプリ（デスクトップアプリの予定タスク）で、メインのチェックアウトが作業ブランチのときの動きはまだ確かめていない（メインのチェックアウトを別のセッションが使っていたため）。確かめることは [`criteria.md`](./criteria.md) 6.2（F1〜F3）、手順は [`plan.md`](./plan.md) 7.3 の3。

- いちばん簡単なのは、ユーザーが作業ブランチをチェックアウトしたまま夜を越した日の翌朝に、次を確かめること：`git log --oneline -3 master`（進捗ログのコミットがmasterにある）、`git log --oneline master..<作業ブランチ>`（進捗ログのコミットが無い）、`git rev-parse --abbrev-ref HEAD`（作業ブランチのまま）、`git config --get --default none progress-report.return-branch`（`none`）。
- 書き込みが要る日（masterに新しいコミットがある日、期間の区切りの日、3日ごとの次回予定日の質問の日）でないと、タスクは切り替えずに終わる（それも正しい動き）。
- 承認待ちで止まっていた場合（`git switch -` などが許可ルールに一致しなかった場合）は、アプリの予定タスクの実行の一覧で、そのセッションが承認待ちになっている。そのときは一度だけ許可し（「always allow」は選ばない）、`docs/issues/closed/27-progress-log-master/plan.md` 4.3 を見直す。

## 2. コミットの Co-Authored-By のモデル名（小さな課題）

- 旧・新のプロンプトとも、コミットの3つ目の `-m` は「Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>」の固定の文。旧プロンプトの実行では、タスクのセッションが実際のモデル名に書き換えていたが、新しいプロンプトはコマンドの形を厳密に指定したので、予行では全コミットがこの固定の文になった（eval-report-1.md 8章の1）。
- 直すなら：プロンプトの文を、タスクのセッションの実際のモデル名に替える（タスクのモデルの設定と合わせる）か、「実際のモデル名を書く」と指示する。コマンドの形は `git commit -m *` のままなので、許可ルールは変わらない。直した後は、予行（`rehearsal/run-all.sh`）を流し直す。

## 3. Writeツールの許可ルール（気づき。issueにするかはユーザーが決める）

- 仕組みの確認（S0）で、Writeツールは `Edit(…)` のルールで許され、`Write(…)` だけのルールは効かないことが分かった（criteria.md 2章）。本番で進捗ファイルを書けているのも `Edit(…)` のルールのおかげ。`settings.local.json` の `Write(…/docs/progress/**)` は今は効いていないが、害はない。

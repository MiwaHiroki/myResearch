このタスクは、`docs/progress/` 配下の進捗ログを、gitのコミット履歴から自動的に追記・更新するための日次バッチである。**進捗ログは常にmasterの履歴を読み、masterにコミットする**（チェックアウト中のブランチ（HEAD）を基準にしない）。ユーザーは2週間に一度これを見てGoogleスライドの進捗報告資料を作る。以下の手順を **順番に、省略せず** 実行すること。会話の記憶はゼロなので、このプロンプトの説明だけで完結させること。

## 前提知識
- 状態ファイルは `docs/progress/.state.json`。フィールド: `current_file`（`docs/progress/`直下の現在の期間ファイル名）、`period_start`（その期間の開始日 `YYYY-MM-DD`）、`next_report_date`（次回の進捗報告・打ち合わせ予定日 `YYYY-MM-DD` またはnull）、`last_commit`（前回処理済みの最新コミットSHA）、`next_report_date_last_asked`（直近でPush通知した日付 `YYYY-MM-DD` またはnull）。
- **ファイル命名規則**: `current_file`は常に`<period_start(YYYY-MMDD形式)>_<X>.md`という`YYYY-MMDD_MMDD`パターンに従う。`X`は、`next_report_date`が設定されていればその`MMDD形式`（例: `1006`）、`next_report_date`が`null`の間は**文字列`MMDD`そのまま**（プレースホルダー、実際の日付ではなく「未定」を示すリテラル文字列）とする。例: 開始日2026-08-10で次回予定日未定なら`2026-0810_MMDD.md`、予定日が2026-10-06に決まれば`2026-0810_1006.md`。この命名は`next_report_date`の値と常に一致していなければならない。このタスクの実行中に`next_report_date`を変更する手順（7b）では、ファイル名もそれに追従させる。
- 各期間ファイルは以下の構成:
  ```markdown
  # 進捗ログ（<period_start> 〜 <next_report_dateがあれば「<next_report_date>予定」、無ければ空欄>）

  ## まとめ
  - (テーマ単位の箇条書き。期間全体を通じた大まかな要約)

  ## 日次ログ

  ### YYYY-MM-DD
  - (その日のコミットの要約、原則1コミット1行)
  ```
- **基準はmaster（HEADではない）**: 新しいコミットは、masterのfirst-parentの履歴（コマンド5）から読む。`last_commit`は、常にmasterのfirst-parentの履歴の上にあるコミットを指す。手順2（判定）では、作業ツリーの`docs/progress/`を読まない（作業ブランチでは古いことがある）。masterの`.state.json`はコマンド3で読む。
- **作業ブランチをチェックアウト中のとき**: まずブランチを切り替えずにmasterの状態を読み（手順2）、書き込みが要る日だけ、追跡されているファイルに未コミットの変更が無いことを確かめてから、一時的に`master`へ切り替える（手順3）。コミットしたら、元のブランチへ戻す（手順5）。切り替える前に、元のブランチ名をgitの設定のキー`progress-report.return-branch`に記録し、戻ったら消す（途中で止まったとき、次の実行で気づくため）。未コミットの変更があれば切り替えず、その日は見送って通知する。
- **タスク自身のコミット**: 件名が「進捗ログ自動更新（」または「進捗期間を区切り、新しい期間ファイルを開始（」で始まるコミットは、このタスク自身のコミットである。日次ログに載せず、「やること」にも数えない。
- `docs/git-rules.md`に「進捗ログ自動更新に限り、このスケジュールタスクによる自動commitを許可する」という例外規定が明記済み。それ以外のファイルは絶対に無断でcommitしないこと（対象はこのタスクで触るファイルのみ）。push は絶対にしないこと。**コミットは常にmasterに対して行う。**
- **このタスクは人が承認できない深夜に自動実行される。** 使うツール・コマンドは、下の「使ってよいコマンドの一覧」のgitコマンドと、Read（このリポジトリの中）、Write・Edit（`docs/progress/`の中だけ。進捗ファイルと`.state.json`はWriteかEditで書く）、`PushNotification`に厳密に収め、それ以外の操作が必要になった場合は実行せず、何もせずに終了して次回に持ち越すこと（無理に別の方法で代替しない。手順3でmasterに切り替えた後なら、終わる前に手順5を行う）。

### 使ってよいコマンドの一覧
**これ以外のコマンドは使わない。** 1回のツール呼び出しにつき1コマンド。`;`・`&&`・`|`でつながない（コマンド5・6の書式の中の`|`は、引用符の中なので、そのまま書く）。`2>&1`などのリダイレクトや`-C`を付けない。Bashツールを使う。`<…>`は実際の値に置き換え、一覧に無いオプションを足さない（形が崩れると、承認待ちで深夜に止まる）。

読み取り（何も変えない）:
- コマンド1: `git config --get --default none progress-report.return-branch` — 前回の記録を読む（手順1-1）
- コマンド2: `git rev-parse --abbrev-ref HEAD` — チェックアウト中のブランチを読む（手順1-2、5-3）
- コマンド3: `git show master:docs/progress/.state.json` — masterの状態ファイルを読む（手順2-1）
- コマンド4: `git merge-base <last_commit> master` — last_commitがmasterの祖先かを確かめる（手順2-2）
- コマンド5: `git log <last_commit>..master --first-parent --date=short --pretty=format:"%H|%ad|%P|%s" --reverse` — masterの新しいコミットを読む（手順2-3）
- コマンド6: `git log <親1>..<親2> --date=short --pretty=format:"%h|%ad|%P|%s" --reverse` — mergeの中身を読む（手順2-4）
- コマンド7: `git status --porcelain --untracked-files=no` — 追跡されているファイルの未コミットの変更を読む（手順3）
- コマンド8: `git status --porcelain -- docs/progress/` — docs/progressの未コミットの変更を読む（手順2-5、3、5-1）
- コマンド9: `git rev-parse master` — コミットする前のmasterの先端を読む（手順4-3）

書き込み:
- コマンド10: `git config progress-report.return-branch <ブランチ名>` — 元のブランチを記録する（手順3）
- コマンド11: `git config --unset progress-report.return-branch` — 記録を消す（手順1-3、3、5-3）
- コマンド12: `git switch master` — masterに切り替える（手順3）
- コマンド13: `git switch -` — 元のブランチに戻る（手順5-2）
- コマンド14: `git add docs/progress/<ファイル> [docs/progress/<ファイル> ...]` — コミットするファイルを追加する（手順4-6）
- コマンド15: `git mv docs/progress/<旧> docs/progress/<新>` — 期間ファイルを改名する（手順4-5の7b）
- コマンド16: `git commit -m "<件名>" -m "<本文>" -m "Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>" -- docs/progress/` — masterにコミットする（手順4-6）。`commit`の直後は必ず`-m`とし、`-q`・`--quiet`・`-a`等のオプションは付けない。**末尾の`-- docs/progress/`は必ず付ける。**

## 手順

### 手順1 状況を確かめる（何も変えない）
- 1-1 コマンド1を実行し、出力を R とする（前回の記録。記録が無ければ `none` が出る）。
- 1-2 コマンド2を実行し、出力を CUR とする（チェックアウト中のブランチ。masterなら `master`、作業ブランチならその名前、detached HEAD なら `HEAD`）。
- 1-3 R が `none` でないとき:
  - CUR が `master` → 通知N2を送り、何も変えずに終わる（前回の実行が、masterに切り替えた後に止まった）。
  - CUR が `master` でない → コマンド11で記録を消して、手順2へ進む（前回は、元のブランチに戻った後に止まっただけ）。

### 手順2 masterの状態を読み、今日やることを決める（何も変えない。ブランチは切り替えない）
- 2-1 コマンド3を実行し、出力（masterの`.state.json`）を S とする。出力が読めない（エラー）、JSONとして壊れている、`S.last_commit` が null のいずれかなら、通知N5を送って終わる。
- 2-2 `<last_commit>` に `S.last_commit`（40桁）を入れてコマンド4を実行する。出力が `S.last_commit` と一致しない（エラーを含む）なら、通知N4を送って終わる（last_commitがmasterの祖先でない）。
- 2-3 `<last_commit>` に `S.last_commit` を入れてコマンド5を実行し、出力を新しいコミットの一覧 LIST とする（1行が1コミットで、古い順。各行は「フルハッシュ|Author Date|親のハッシュ（空白区切り）|件名」）。LIST が空でなければ、1行目の親のハッシュの1つ目が `S.last_commit` と一致することを確かめる。一致しなければ、通知N4を送って終わる（last_commitがmasterのfirst-parentの履歴の上にない）。
- 2-4 LIST の各行を、次のように分ける。
  - タスク自身のコミット（件名が「進捗ログ自動更新（」または「進捗期間を区切り、新しい期間ファイルを開始（」で始まる）は除く。
  - 親のハッシュが2つある行（merge）は、1つ目を `<親1>`、2つ目を `<親2>` に入れてコマンド6を実行し、中身を読む。中身から、merge（親のハッシュが2つある行）とタスク自身のコミットを除く。除いた後に中身が空になれば、そのmergeも除く。
  - 残ったものを「載せるコミット」とする（mergeは、残った中身と合わせて1件と数える）。
- 2-5 今日の日付を TODAY（`YYYY-MM-DD`）とし、次の (A)〜(D) を判定する。
  - (A) 載せるコミットが1件以上ある。
  - (B) `S.next_report_date` が null でなく、かつ `TODAY >= S.next_report_date`（期間の区切り。手順4-5の7b）。
  - (C) `S.next_report_date` が null で、かつ（`S.next_report_date_last_asked` が null、または TODAY との差が3日以上）（次回予定日の質問。手順4-5の7c）。
  - (D) CUR が `master` で、コマンド8の出力が空でない（前回の実行の残り）。
  - どれにも当たらなければ、ここで終わる（ブランチを切り替えない。通知しない。ファイルも変えない）。
- 2-6 (A) があれば、「日次ログの書き方」に沿って、追記する行の文の下書きを作っておいてよい（見出しの日付は、手順4-1で読み直したファイルで決める）。

### 手順3 作業する場所を用意する
CUR に応じて、次のどれか1つを行う。
- CUR が `HEAD`（detached HEAD）: 通知N1（理由: 「detached HEADである」）を送って終わる。
- CUR が `master`:
  - コマンド7を実行する。出力に未マージの行（行頭の2文字に `U` がある、または行頭の2文字が `AA`・`DD`）があれば、通知N1（理由: 「masterでマージやcherry-pickが途中である」）を送って終わる。
  - コマンド8を実行する。出力に変更があれば（前回の実行が途中で中断された可能性がある）、まずその内容を確認し、`.state.json`や進捗ファイルの内容として矛盾がなければ、そのまま今回の分としてcommitに含めてよい（作り直す必要はない。残りの日次ログに、載せるコミットがすでに書かれていれば、手順4-2で同じ行を二重に書かない）。矛盾があれば、通知N5を送って終わる。
  - docs/progressの外に未コミットの変更（ステージ済みを含む）があっても構わない（コミットはdocs/progressだけなので混ざらない）。手順4へ進む。
- CUR がそれ以外（作業ブランチ。以下、このブランチ名を B とする）:
  - コマンド7を実行する。出力が空でなければ、通知N1（理由: 「追跡されているファイルに未コミットの変更がある」）を送って終わる（ブランチを切り替えない）。追跡されていないファイルだけなら、出力は空になる（そのまま進んでよい）。
  - 出力が空なら、`<ブランチ名>` に B を入れてコマンド10を実行し（記録）、続けてコマンド12を実行する。
    - コマンド12が失敗したら、コマンド11で記録を消し、通知N1（理由: 「masterに切り替えられなかった（<gitのメッセージの要約>）」）を送って終わる。
    - 成功したら、手順4へ進む。これ以降は、手順4の途中でエラーになったときも、必ず手順5を行ってから終わる。

### 手順4 進捗ログを書き、masterにコミットする（基準は常に `master`）
- 4-1 Readで `docs/progress/.state.json` と `docs/progress/<current_file>` を読み直す（手順3で切り替えた場合は、中身も更新日時も変わっているので、Edit・Writeの前に必ず読み直す）。手順3で切り替えた場合は、読んだ`.state.json`が手順2-1の S と同じ内容であることを確かめる。違えば通知N5を送り、手順5へ進む。
- 4-2 (A) があれば、「日次ログの書き方」に沿って `docs/progress/<current_file>` の「## 日次ログ」セクションの末尾に追記する。続けて、追記後の「## 日次ログ」全体を読み直し、「## まとめ」セクションをテーマ単位の箇条書きで**再生成して丸ごと置き換える**（期間全体のダイジェスト。スライド作成時に一番参照される部分なので、簡潔かつ内容が分かるように）。
- 4-3 コマンド9を実行し、出力（この実行でコミットする前のmasterの先端のフルSHA）を、`.state.json` の `last_commit` に書く。これは、この実行の最初のコミットの前に一度だけ行う（(A) が無く、手順4-5だけでコミットする場合も、ここで書く。この実行で2件コミットする場合も、2件目の前に値を変えない）。
- 4-4 (A) があるか、手順3で前回の残り（(D)）を含めたときは、手順4-6の形で1件コミットする（件名は「コミットの件名と本文」の「日次ログ」）。
- 4-5 次回予定日の確認・通知判定（旧手順7。コミットの有無に関わらず毎回実施。**b, cは`next_report_date`の値によって排他的に分岐する**。手順2-5の (B) が7b、(C) が7cに当たる。TODAY は手順2-5と同じ日付。7bでは、通知の送信と`next_report_date_last_asked`の更新を済ませてから、1回だけコミットする）:
   - 7b. `.state.json`の`next_report_date`が設定されており（nullでない）、かつ `TODAY >= next_report_date` の場合（期間の区切りに到達）:
      - 目標のファイル名を `docs/progress/<period_start(YYYY-MMDD形式)>_<TODAYのMMDD>.md` とする（`next_report_date`ではなく**実際に処理した日であるTODAY**を使う。両者が同じ日なら現在のファイル名と一致するはずである）。
      - 現在の`current_file`のパスがこの目標ファイル名と異なる場合のみ、`git mv docs/progress/<current_file> <目標ファイル名>` でリネームする（一致していれば何もしない）。
      - リネーム後（またはリネーム不要だった場合はそのまま）、そのファイルの1行目の見出しを `# 進捗ログ（<period_start> 〜 <TODAY>）`（「予定」は付けない。実績の終了日のため）に更新する。
      - 新しい期間ファイル `docs/progress/<TODAYのYYYY-MMDD形式>_MMDD.md`（`next_report_date`はまだ`null`なので、末尾は実日付ではなくプレースホルダー文字列`MMDD`のまま）を、上記のテンプレート（`period_start`はTODAY、見出しは`# 進捗ログ（<TODAY> 〜 ）`、まとめ欄は空の箇条書き1行「(次回追記待ち)」、日次ログ欄は見出しのみ）で新規作成する。
      - `.state.json`の`current_file`を新しいファイル名（`<TODAYのYYYY-MMDD形式>_MMDD.md`）に、`period_start`をTODAYに更新し、`next_report_date`を`null`に戻す。
      - 上記で変更・作成・リネームしたファイルをまとめてコマンド14で追加し、「進捗期間を区切り、新しい期間ファイルを開始（YYYY-MM-DD）」という1コミットを作る（手順4-6の形）。
      - `next_report_date`が`null`に戻ったので、続けて`PushNotification`ツールで「進捗レポート: 次回の進捗報告・打ち合わせ予定日はいつですか？決まったら教えてください。」（200字以内、日本語、1行）を送信する（`next_report_date_last_asked`の間隔チェックは無視し、今回は必ず送る）。`.state.json`の`next_report_date_last_asked`をTODAYに更新し、変更をcommitに含める。
      - **この場合は次のcを実行しない。**
   - 7c. **bに該当しない場合**（＝`next_report_date`が`null`、または設定済みだが`TODAY`がまだ`next_report_date`未満）のうち、**`next_report_date`が`null`であり、かつ（`next_report_date_last_asked`が`null`、または`TODAY`との差が3日以上）**の場合のみ:
      - `PushNotification`ツールで「進捗レポート: 次回の進捗報告・打ち合わせ予定日はいつですか？決まったら教えてください。」（200字以内、日本語、1行）を送信する。
      - `.state.json`の`next_report_date_last_asked`をTODAYに更新し、変更をcommitする（手順4-6の形。件名は「コミットの件名と本文」の「通知の記録だけ」。手順4-4でコミットした後なら、これは2件目のコミットになる）。
      - **`next_report_date`が既に設定済み（null でない）でTODAYがまだそれ未満の場合は、通知は送らない（何もしない）。** これが最も多いケースであることに注意。
   - 7d. 上記b・cのいずれにも該当しない場合は何もしない。
- 4-6 コミットの形: コマンド14で、そのコミットで変更・作成したファイルを追加する（コマンド15で改名したファイルは、新しい名前だけを指定する）。続けてコマンド16でコミットする（**push はしない**）。**末尾には必ず `-- docs/progress/` を付ける**（docs/progressのほかにステージされている変更を、コミットに混ぜないため）。件名と本文は「コミットの件名と本文」のとおり。

### 手順5 元のブランチに戻す（手順3で切り替えたときだけ行う。手順4の途中でエラーになったときや、手順4-1で通知N5を送ったときも、ここを行う）
- 5-1 コマンド8を実行し、出力が空であることを確かめる。空でなければ、元のブランチに戻らず、通知N3（理由: 「進捗ログの変更がコミットされずに残っている」）を送って終わる（記録は消さない）。
- 5-2 コマンド13を実行する。失敗したら、通知N3（理由: 「<gitのメッセージの要約>」）を送って終わる（記録は消さない）。並行のセッションの変更（docs/progress以外）は、gitが元のブランチへ持ち帰る。持ち帰れない場合は、gitが止まる。
- 5-3 コマンド2を実行し、出力が B であることを確かめてから、コマンド11で記録を消す。B でなければ、通知N3（理由: 「戻った先のブランチが <コマンド2の出力> だった」）を送って終わる（記録は消さない）。

## 日次ログの書き方
- 載せるのは、手順2-4の「載せるコミット」だけ。タスク自身のコミットは書かない。
- 1件は、LIST（masterのfirst-parentの履歴）の1行に当たる。LIST の順（古い順）に書く。
  - ふつうのコミット: **原則1コミット1行、コミットのsubjectをベースに簡潔な日本語で記載する**（生ログが基本）。内容がほぼ同一とみなせる連続コミット（例:微修正の繰り返し）に限り1行にまとめてよい（例:「〜を微修正（3コミット）」）。
  - merge:
    - 親の行: GitHubのPRのマージ（件名が「Merge pull request #NN …」）は「PR #NNをmerge（<内容の要約>、Nコミット、MM-DD〜MM-DD）」と書く（Nは、手順2-4で除いた後の中身の数。MM-DD〜MM-DDは、その中身のAuthor Dateの最初と最後）。GitHubのmasterのpullによる取り込み（件名が「Merge branch 'master' of …」）は「GitHubのmasterを取り込み（PR #NN を含む、Nコミット）」と書く（PR #NN は、中身にある「Merge pull request #NN …」の番号。複数あれば「PR #NN・#MM を含む」とする）。それ以外のmergeは「<ブランチ名>をmerge（<要約>）」と書く。
    - 子の行（親の行の下に、2文字下げた箇条書き）: 中身のコミット（mergeとタスク自身のコミットを除く）を、原則として1コミット1行で書き、行末に `（MM-DD）`（そのコミットのAuthor Date）を付ける。ほぼ同じ内容の連続したコミットは、1行にまとめてよい。
- 見出しの日付: これから書くコミット（mergeは親の行）のAuthor Date（LIST の2列目）を d、そのときの日次ログの末尾の見出し（`### YYYY-MM-DD`）の日付を LH とする。1件書くたびに、LH を見直す。
  - 見出しが1つも無い、または d > LH: 末尾に `### d` の見出しを足し、その下に書く。
  - d = LH: 新しい見出しは作らない。末尾の見出しの下の、最後の行に続けて書く。
  - d < LH（cherry-pick、rebase、fast-forwardで古い日付のコミットが入った場合）: 新しい見出しは作らない。末尾の見出し（LH）の下の、最後の行に続けて書き、行末に `（MM-DDのコミット）`（MM-DDは d）を添える。
  - こうすると、見出しは日付順に並び、同じ日付の見出しは2つできない。
- **既存の日次ログの内容は絶対に書き換えない**（追記のみ、履歴として不変）。

例（PRのマージ。中身のうち3件だけを示す）:

```markdown
### 2026-10-19
- PR #26をmerge（溝の自動追跡 issue #25：trackGroove・grooveTrack_1cycle.mの実装、評価1回目で合格、振り返り。9コミット、10-12〜10-19）
  - issue #25の受け渡しフォルダを作成（10-12）
  - 写真1枚の範囲で溝を自動追跡する`trackGroove`と`grooveTrack_1cycle.m`を実装（10-13）
  - issue #25の受け渡しフォルダを`docs/issues/closed/`へ移動（10-19）
```

## 通知の文
`PushNotification`ツールで送る。200字以内、日本語、1行。`<…>`は実際の値に置き換える。gitのメッセージやエラー内容は、60字以内に要約する。

- N1（持ち越し。手順3）: 「進捗ログ自動更新: <理由>ため、今回は見送りました（チェックアウト中: <CUR>）。」。<理由>は手順3に書いたもの。その日に (B) か (C) に当たる場合は、同じ文の後ろに「次回の進捗報告・打ち合わせ予定日はいつですか？」を続ける。
- N2（前回の中断。手順1-3）: 「進捗ログ自動更新: 前回の実行が途中で止まり、チェックアウトがmasterのままです（元のブランチ: <R>）。確かめて戻したら git config --unset progress-report.return-branch を実行してください。」
- N3（戻れない。手順5）: 「進捗ログ自動更新: masterに切り替えた後、元のブランチ <B> に戻れませんでした（<理由>）。チェックアウトはmasterのままです。確認をお願いします。」。<理由>は手順5に書いたもの。
- N4（last_commitの異常。手順2-2・2-3）: 「進捗ログ自動更新: last_commit（<S.last_commitの先頭7桁>）がmasterのfirst-parentの履歴に無いため、更新を止めました。確認をお願いします。」
- N5（その他の異常）: 「進捗ログ自動更新でエラーが発生しました。確認をお願いします: (エラー内容)」
- 次回予定日の質問（手順4-5の7b・7c）: 「進捗レポート: 次回の進捗報告・打ち合わせ予定日はいつですか？決まったら教えてください。」

## コミットの件名と本文
- 件名:
  - 日次ログ（手順4-4）: 「進捗ログ自動更新（<最後に追記した見出しの日付>分）」
  - 通知の記録だけ（手順4-5の7c）: 「進捗ログ自動更新（<TODAY>、通知の記録）」
  - 期間の区切り（手順4-5の7b）: 「進捗期間を区切り、新しい期間ファイルを開始（<TODAY>）」
- 本文（どの件名でも同じ）: 「深夜バッチ（scheduled task: progress-report-daily）による自動commit。docs/git-rules.mdの自動commit例外規定に基づく。masterに直接コミット（チェックアウト中: <CUR>）。」。<CUR> は手順1-2の CUR（作業ブランチから切り替えた場合は、元のブランチ名 B）。
- 3つ目の`-m`は「Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>」。
- 件名と本文には、二重引用符・バッククォート・ドル記号・改行を入れない。
- 件名の先頭の2つの形（「進捗ログ自動更新（」「進捗期間を区切り、新しい期間ファイルを開始（」）は、タスク自身のコミットの見分けに使う。この形を変えない。
- 例（作業ブランチ claude/xxx から切り替えた日の、日次ログのコミット。コマンド16の形）: `git commit -m "進捗ログ自動更新（2026-10-22分）" -m "深夜バッチ（scheduled task: progress-report-daily）による自動commit。docs/git-rules.mdの自動commit例外規定に基づく。masterに直接コミット（チェックアウト中: claude/xxx）。" -m "Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>" -- docs/progress/`

## 注意事項
- 各git操作の前に必ず対象ファイルの現在の中身を読み、意図しない上書きをしていないか確認すること。
- 何らかの理由で手順が実行できない・状態ファイルが壊れている等の異常時は、無理に推測で書き換えず、`PushNotification`で「進捗ログ自動更新でエラーが発生しました。確認をお願いします: (エラー内容)」と通知し、ファイルは変更しないこと。
- 手順3でmasterに切り替えた後にエラーになったら、手順5を試みてから通知する。
- ブランチを切り替えるのは、手順3のコマンド12と、手順5のコマンド13だけ。
- 絶対にpushしないこと。`docs/progress/`以外のファイルを変更・commitしないこと。

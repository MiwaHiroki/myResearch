# 進捗報告の素材を作る

進捗報告は、実装の現状・限界・不明点を指導教員に伝え、一緒に考察するための場である（`docs/rules/slides.md` の「進捗報告の目的」）。そこで使う図は、issue が終わってから思い出して作るより、作業の区切りで、内容をいちばんよく分かっているときに作るほうが確かである。図と、図が何を示すかを書いた文は、ユーザーが実装の中身を理解する助けにもなる。

この skill は、作業の区切りごとに図の候補を出し、ユーザーが選んだ図を用意し、素材ファイルにためていく手順である。ルールの中身は次の文書が正なので、この skill には手順だけを書き、ルールを書き写さない。

| 決まりごと | 文書 |
|---|---|
| 素材ファイルの書き方 | `docs/issues/README.md` の「progress-material.md の書き方」 |
| 図の置き場所・名前、進捗報告用の図の体裁、作業用の図を写してよい条件 | `docs/rules/figures.md` |
| 進捗報告の目的、図の説明の文言、強調の図形 | `docs/rules/slides.md` |
| 段階の流れの中での位置 | `docs/staged-development.md` の 5.7 |
| illustrator が書いてよい範囲 | `.claude/agents/illustrator.md` |

## 言葉

- **素材**：進捗報告で使う図か表の1つ。素材ファイルの中で `M1`、`M2` … の番号で呼ぶ。
- **素材ファイル**：受け渡しフォルダ `docs/issues/<番号>-<slug>/` の `progress-material.md`。素材を、スライドの説明の順に並べてためる。
- **区切り**：素材の候補を出す時点。段階的な開発の、計画の承認と、評価の合否の確認の2つ。
- **作業用の出力先**：評価スクリプトなどが図を出す、git の管理外の場所（今は `results/<MMDD>/`）。
- **進捗報告用の置き場所**：進捗報告用の図とスクリプトを置く、git で管理する場所。`docs/rules/figures.md` の「置き場所と用途」の表が決める（今は図が `results/figures/progress/<テーマ>/`、スクリプトが `scripts/progress/`）。

## 1. 使う場面と対象

- (a) 段階的な開発の区切りで使う。計画の承認では問題・原因・方法の図を、評価の合否の確認では結果・考察の図を扱う。
- (b) ユーザーが図を頼んだときは、どの段階でも使う。

素材を作るのは、研究の内容に関わる issue だけにする。開発の環境やルールの整備は、スライドに載せないためである（`docs/rules/slides.md`）。作るかどうかは、準備の段階でユーザーに確かめ、受け渡しフォルダの `README.md` の作業履歴の「準備・全体」に **決定** として書く。決定が無いまま区切りに来たら、候補を出す前に確かめる。

受け渡しフォルダが無い作業（小さな issue、issue の無い作業）では、素材ファイルを作らない。頼まれた図は、skill `make-figure` で進捗報告用の図として作る。

## 2. 候補を出す

1. その区切りの成果物を読む。
   - (a) 計画の承認では、`plan.md` の結論・調査結果・案の比較を読み、計画担当が確認に使った図（`temp/` にあり、作り方は `plan.md` の付録にある）を見る。
   - (b) 評価の合否の確認では、`eval-report-<n>.md` の結果の表と、ユーザーが判断する項目の図を見る。
2. 使える図がすでにあるかを探す。新しく作るより、時間もトークンも少なくて済むからである。
   - (1) 評価担当などが作業用の出力先に出した図は、`docs/rules/figures.md` の条件を満たせば、そのまま写せる。条件には、名前とタイトルのほかに、体裁（文字と点の大きさ、凡例の位置）がほかの素材とそろうことも含む。
   - (2) 進捗報告用の置き場所に前に作った図があれば、名前・タイトル・体裁を同じ条件で確かめてから使う。満たさなければ、作り直す候補にする。
   - (3) 計画担当が `temp/` に作った図は、名前がルールに沿わず、作ったスクリプトも無いので、写さずに作り直す。
3. 候補を3〜5個に絞る。区切りごとに、次の型から選ぶ。
   - (a) 計画の承認
     - 症状の例。何が困るのかを示す（例：音声の波形に出た外れ値）。
     - 原因の仕組み。なぜ起きるのかを示す（例：写真に溝底範囲を重ねた切り出し、1列の暗さの分布としきい値）。
     - 方法の考え方と、採らなかった案との比べ。表になることが多い。
   - (b) 評価の合否の確認
     - 直す前と後の比べ。同じ場所の図や波形で示す。
     - 数値の表。外れ値の数などを示す。
     - 限界・欠点の例。うまくいかなかった所や、直したことで失ったものを示す。うまくいった所だけを見せないために、必ず1つは入れる。
     - 残った問題と不明点。
4. 候補ごとに、伝えること（スライドのタイトルの案）と示すことを1〜2文で書き、既存の図を写すのか新しく作るのかを添える。

## 3. ユーザーに選んでもらう

1. 候補は、区切りの確認を頼むとき（計画の承認、評価の合否の確認）に一緒に出す。確認の回数を増やさないためである。候補は (a)(b)… で並べる。
2. ユーザーは、作る候補を選び、足りない図を足し、要らない候補を見送る。
3. 決まったことを書く。
   - (1) 素材ファイルが無ければ、`docs/issues/README.md` のひな型で作り、`README.md` のファイル一覧に足す。
   - (2) 素材ごとに項目を作る。状態は、作るものを「依頼」、見送ったものを「見送り」、後で決めるものを「候補」にする。
   - (3) `README.md` の作業履歴の「進捗報告の素材」の見出しに、ユーザーの **決定** を書く。
   - (4) 区切りの決定を反映するコミット（`docs/staged-development.md` 5.1）に含める。

## 4. 図を用意する

1. 用意する時期を決める。
   - (a) 計画の承認の図は、承認のコミットの後、評価基準の段階のエージェントを呼ぶ前に用意する。直す前の状態は、実装の後では再現しにくくなることがあるためである。
   - (b) 評価の合否の確認の図は、合否のコミットの後、仕上げ（振り返り）の前に用意する。
   - (c) ユーザーが頼んだ図は、ほかのエージェントが MATLAB を使っていないときに用意する。MATLAB は1つを共有しているためである。
2. 作り手を決める。
   - (a) 作業用の図を写す素材と、表だけの素材しか無いときは、main が自分で写し、素材ファイルに書く。MATLAB を使わない軽い作業なので、エージェントを呼ばない。写す前に、`docs/rules/figures.md` の写してよい条件を確かめる。
   - (b) MATLAB で図を作る素材があれば、`illustrator` を呼ぶ。1つの区切りの素材は、写す素材も含めて1回の依頼にまとめる。

   出典から写すだけの表の素材と、進捗報告用の置き場所にある既存の図をそのまま使う素材は、(b) のときも main が書く。illustrator には、新しい計算が要る表だけを頼む。main は、illustrator を呼ぶ前に自分の素材を書き終えるか、illustrator が終わってから書く。同じ素材ファイルを同時に書くと、どちらかの変更が消えるためである。
3. illustrator の依頼文は、`docs/staged-development.md` 6章の共通部分に、次のことを足して作る。
   - 用意する素材の一覧（番号、伝えること、示すこと、元にする図・コード・データ、写すか作るか）
   - 進捗報告用の置き場所のテーマ（`docs/rules/figures.md`）
   - 直す前の状態の作り方（保存したデータを読む、パラメータを直す前の値にする、など）。評価の後に、直す前の図を新しく作るときは必ず書く
   - 図の値を照らし合わせる出典（受け渡しファイルの章、評価スクリプトが出した CSV）。食い違ったときは、`.claude/agents/illustrator.md` の「出典との食い違い」に従って報告させる

   依頼文では、ユーザーの決定を「issue作成後にユーザーと決めたこと」に、main が足した指示を「手順・補足」に分けて書く。illustrator が報告で、main の指示をユーザーの決定と取り違えないようにするためである。

## 5. 確かめて、ユーザーに見せる

1. illustrator を呼んだときは、`git status`・`git diff` で、書いてよい範囲の外が変わっていないかを確かめる。
   - illustrator が「出典の誤り」を報告したときは、main も写真や保存したデータで確かめ、ユーザーに伝えて、その素材を使うかを決めてもらう。
   - 閉じた issue の受け渡しファイルは直さず、素材ファイルの示すことに注意として書く。作業中の issue なら、出典を直すかもユーザーに確かめる。
2. 用意した図の PNG を開き、次の点を見る。
   - (1) 名前とタイトルが、描いたものと合っているか（`docs/rules/figures.md` の「種類と条件は、描いたものに合わせる」）
   - (2) 凡例と点・線が重なっていないか、ラベルが見切れていないか
   - (3) 撮影画像の表示範囲が [0 255] のままか
   - (4) 素材ファイルの「示すこと」が、図から読み取れるか
   - (5) 文字と点の大きさ、凡例の位置が、ほかの素材とそろっているか（`docs/rules/figures.md` の「進捗報告用」）。PNG では分かりにくいので、fig を開いて `FontSize`・`SizeData`・凡例の `Location` を測る
3. 素材の状態が「作成済み」になっていることを確かめ（main が写した素材は、ここで「作成済み」にする）、`README.md` の作業履歴に作業の項目を足して、コミットする。ユーザーの確認を待つ間に、追跡されているファイルの変更が夜を越さないようにするためである（`docs/staged-development.md` 5.1）。illustrator が関わったときは、末尾に `Agent: illustrator` と `Agent: main` を書く。
4. 図と「示すこと」をユーザーに見せる。ユーザーが離れた端末から見ていることがあるので、図はファイルとして送るか、パスを示す。表の素材があれば、その番号と素材ファイルのパスを挙げて、表も見てもらう。図だけを送ると、ユーザーが表を見たかが分からず、表を「確認済み」にできないためである。
5. ユーザーの確認の結果を素材ファイルと作業履歴に書き、別のコミットにする。
   - (a) よければ、状態を「確認済み」にする。
   - (b) 直しがあれば、その素材の状態を「依頼」に戻す。同じセッションなら illustrator に続きを頼む（`SendMessage`）。セッションが変わっていたら、直す内容をすべて依頼文に書いて呼び直す。直しの依頼でも、ユーザーの決定と main の指示を分けて書く（4章の3）。直した後に、2〜5 をもう一度行う。

## 6. 仕上げとスライドへのつなぎ

- issue を閉じる前（振り返りの前）に、素材ファイルを見直す。「依頼」や「作成済み」のまま残った素材があれば、ユーザーに確かめる。見直したら、メタデータの状態を「完了」にする。
- 進捗報告のスライドは、skill `make-progress-slides` が、この素材ファイルを材料にして下書きする。素材ファイルの節は、スライドの説明の順と同じに並べてある。

## 7. 気を付けること

- 図に、丸・四角・矢印などの強調の図形を描かない。強調はスライドで描く（`docs/rules/slides.md` の「強調の図形」）。描いてほしい所は、素材ファイルに言葉で書く。
- 図の中身や明るさを変えない（`docs/rules/figures.md` の「撮影画像の表示」）。
- 素材ファイルの数値は、出典の受け渡しファイルと同じ桁で写す。推測と事実を分けて書く（`docs/rules/slides.md` の「文言」）。
- 直したことで失ったものや限界の大きさは、「小さい」などの言葉で済ませず、出典の数値で書く。数値が無ければ、確かめていないと書く。
- `experiments/`・`data/` は読むだけにする（`docs/rules/data.md`）。

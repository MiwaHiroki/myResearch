# 進捗報告のスライドを作る

ルールの中身は [`docs/rules/slides.md`](../../../docs/rules/slides.md) が正で、フォルダの構成・分担・Typst の書き方は [`docs/progress-slides.md`](../../../docs/progress-slides.md) にある。このskillは、それに沿ってスライドを作る手順だけを書く。ルールを書き写さない。

## 1. ルールと前回のスライドを読む

1. `docs/rules/slides.md` と `docs/progress-slides.md` を読む。前に読んでいても、文言の指針が足されていることがあるので読み直す。
2. `slides/progress/` の中で一番新しい回の `.typ` を読み、書き方と流れを合わせる。

## 2. 報告の日付を決める

スライドを作るときも直すときも、毎回この手順で日付を確かめる。報告日は、作り始めた後に決まることがあるためである。

1. 前回の報告日を、`slides/progress/` の中で、日付の決まった最新のフォルダの名前から決める。
2. `docs/progress/.state.json` の `next_report_date`（次回の報告日）を読む。`.state.json` の最新は、常に `master` にある（作業ブランチのものは古いことがある）。
3. 今回の報告日を決める。
   - (a) `next_report_date` が前回の報告日より後なら、それを今回の報告日にする。
   - (b) `next_report_date` が空か、前回の報告日と同じかそれより前なら（前回の報告日のまま、まだ更新されていない）、今回の報告日は未定とする。未定のときは、日付の代わりに文字列 `MMDD` を使う。年は、作り始めた日の年にする（例：フォルダ `slides/progress/2026-MMDD/`、本体 `2026MMDD.typ`、表紙の日付 `2026/MM/DD`）。
4. 報告のフォルダが `MMDD` のままで、今回の報告日が決まっていたら、日付を直す。
   - (1) `git mv` で、フォルダと `.typ`・PDF の名前を変える。
   - (2) スライドの中の今回の日付を直す。表紙の日付、2枚目のタイトルの右側、最後のスライドのタイトルの左側、ファイルの先頭のコメントにある。
   - (3) PDF を作り直す（7.）。
5. どの期間ファイルを材料にするかを決める。期間ファイルの最新も、常に `master` にある。

## 3. 報告のフォルダを作る

1. `slides/progress/<YYYY-MMDD>/` を作る（`<YYYY-MMDD>` は今回の報告日。未定なら `<YYYY>-MMDD`）。
2. 本体を `<YYYYMMDD>.typ` という名前で作る。先頭で、テンプレートを読み込む。

   ```typst
   #import "../../template/progress.typ": *
   #show: progress-slides
   ```

3. 図を載せるなら `figures/` を、ユーザーが過去のスライドの画像を置くなら `copied/` を、音声や `.fig` を見せるなら `extras/` を作る。

## 4. 下書きを書く

材料は、進捗ログの期間ファイル、`results/figures/progress/` の図、関係する issue の受け渡しフォルダ（`docs/issues/`）である。スライドは、次の順に並べる。

1. 表紙：`#title-slide(date: "YYYY/MM/DD")`
2. 前回の ToDo：前回の `.typ` の最後の `#slide(...)` を、ソースごとコピーする。
   - (1) タイトルの `MM/DD` を、今回の報告日にする（未定なら `MM/DD` のまま）。
   - (2) 項目を、進捗ログをもとに進み具合で分ける（11/17 の回では「完了」と「未着手」）。この分け方は下書きとして、報告でユーザーに確かめてもらう。
   - (3) `copied-from` は付けない。
   - (4) 前回の最後のスライドが空のまま（ToDo が書かれていない）なら、空のままコピーし、報告でユーザーに伝える。
3. 詳細：実装した内容と考察を、図と説明で示す。
4. 次回までの ToDo：タイトルは「今回の日付 → 次回の日付」とし、次回の日付は `MM/DD` と書く。中身は空の箇条書き（`- #sym.zws`）にする。打ち合わせの後に、ユーザーが ToDo を書く。

下書きを書くときは、次のことに気を付ける。

- 実装に関係しない事項（論文の共有、学会の申し込みなど）は、ユーザーが書く。Claude は、頼まれない限り書かない。
- 研究の内容に関係しないもの（開発の環境やルールの整備：CI、エージェント、文書など）は、進捗ログに載っていても、スライドに載せない。載せるのは、ユーザーがはっきり指定したときだけである。
- 文言の指針が `docs/rules/slides.md` にあれば、それに従う。

## 5. 図を置く

1. 載せる図を、`figures/` にコピーする。元のファイル名を変えない（図の下に出るファイル名が、元の図を探す手がかりになるため）。
2. 図は `fig-at` と配置の型（`cell-left`・`cell-right`・`cell-full`・`cell-side`）で置く。
3. 強調の図形が要るときは、図の PNG を見て位置を割合で決め、`marks:` に書く。図と図の間の矢印は `#draw` で描く。図形の位置は仮のものとして、報告で伝える。

## 6. 過去のスライドを入れる

コピーするスライドは、ユーザーが決める。

- (a) ユーザーが `copied/` に画像を置いたときは、`#copied-slide(image("copied/<MMDD>_p<N>.png"))` で入れる。ファイル名が `<MMDD>_p<N>` の形でなければ、ユーザーに確かめる。
- (b) Typst で作った回のスライドを指定されたときは、その回の `.typ` から `#slide(...)` をコピーし、`copied-from: "MM/DD"` を足す。使っている図も、今回の `figures/` にコピーする。

## 7. PDF を作り、確かめる

1. リポジトリの直下で、PDF を作る。

   ```bash
   typst compile --root slides slides/progress/<YYYY-MMDD>/<YYYYMMDD>.typ
   ```

2. ページ数が、作ったスライドの数と同じかを確かめる。違えば、本文がはみ出したページがある。
3. すべてのページを PNG にして（PyMuPDF の `get_pixmap` など）、目視で確かめる。見る点は `docs/rules/slides.md` の「確かめること」にある。画像はスクラッチパッドに書き出し、報告のフォルダには置かない。

## 8. コミットと報告

1. `git branch --show-current` でブランチを確かめる。
2. 報告のフォルダ（`.typ`、PDF、`figures/`、`copied/`、`extras/`）をコミットする。push はユーザーに確かめてからにする。
3. 報告には、次のことを書く。
   - 作ったスライドの一覧（ページ番号とタイトル）
   - 仮の位置に置いた強調の図形
   - ユーザーに決めてもらうこと（載せるかどうか迷った項目、文言、2枚目の進み具合の分け方）
   - アップロードするファイル（報告のフォルダのうち `.typ` 以外）

## 9. 打ち合わせの後に ToDo を書く

ユーザーから打ち合わせで決まった ToDo を伝えられ、書くよう頼まれたときの手順である。

1. 2.の手順で日付を確かめる。次回の報告日が決まっていれば、最後のスライドのタイトルの `MM/DD` をその日付にする。
2. 最後のスライドに、ToDo を箇条書きで書く。ユーザーの言葉を変えずに書く。
3. PDF を作り直して確かめ（7.）、コミットする（8.）。
